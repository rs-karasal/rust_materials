# 27. Конкурентность: `join!`, `select!` и типичные грабли

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Основы асинхронности мы разобрали. Теперь — инструменты, из которых складываются реальные асинхронные программы: ожидание первого из нескольких событий, таймауты, обмен данными между задачами. И отдельно то, на чём спотыкаются почти все.

## `select!` — кто первый

`join!` из прошлой статьи ждёт **все** задачи. Иногда нужна первая:

```rust
tokio::select! {
    r = work(1, 50) => println!("первым пришёл {r}"),
    r = work(2, 200) => println!("первым пришёл {r}"),
}
```

```
первым пришёл 1
```

`select!` запускает все ветви одновременно, выполняет тело победившей, а **остальные отменяет**.

Отмена — важное свойство. Асинхронная задача в Rust прерывается на любой точке `.await`, и незавершённая работа просто исчезает. Отсюда практическое следствие: не помещайте в ветви `select!` операции, которые нельзя обрывать посередине — например, запись в файл или транзакцию.

Типичное применение — обработка сигнала завершения:

```rust
tokio::select! {
    _ = server.run() => {},
    _ = tokio::signal::ctrl_c() => println!("получен Ctrl-C, выключаемся"),
}
```

## Таймауты

Частный случай, встроенный в tokio:

```rust
match timeout(Duration::from_millis(50), work(3, 500)).await {
    Ok(v) => println!("успели: {v}"),
    Err(_) => println!("не успели за 50 мс"),
}
```

```
не успели за 50 мс
```

`timeout` оборачивает будущее и возвращает `Result`: `Ok` с результатом либо `Err`, если время вышло. Задача при этом отменяется.

Правило для сетевого кода: **любой внешний вызов оборачивайте в таймаут**. Зависший запрос без него удерживает задачу навсегда, и рано или поздно они накапливаются до отказа сервиса.

## Асинхронные примитивы синхронизации

У tokio есть свои `Mutex`, `RwLock` и каналы. Отличие от стандартных — они **не блокируют поток**, а приостанавливают задачу:

```rust
let counter = Arc::new(Mutex::new(0));

for _ in 0..5 {
    let c = Arc::clone(&counter);
    tokio::spawn(async move {
        let mut guard = c.lock().await;      // .await, а не просто lock()
        *guard += 1;
    });
}
```

Заметьте `.await` после `lock()`. Стандартный `Mutex` в этом месте заблокировал бы поток рантайма вместе со всеми чужими задачами.

При этом — неожиданный совет: **для коротких критических секций берите обычный `std::sync::Mutex`**. Асинхронный мьютекс дороже, а если под замком не происходит `.await`, блокировка длится наносекунды и вреда не приносит. Асинхронный нужен, когда внутри критической секции есть `.await`.

Каналы устроены как в статье 24, но с `.await` и ограниченной ёмкостью:

```rust
let (tx, mut rx) = mpsc::channel(10);

tokio::spawn(async move {
    for i in 0..3 {
        tx.send(format!("событие {i}")).await.unwrap();
    }
});

while let Some(msg) = rx.recv().await {
    println!("{msg}");
}
```

Число 10 — размер буфера. Когда он заполнен, `send` приостанавливается до освобождения места. Это **обратное давление** (backpressure): медленный потребитель автоматически притормаживает быстрого производителя, не давая памяти расти бесконечно. У неограниченных каналов такой защиты нет, поэтому их избегают.

Цикл `while let Some(msg) = rx.recv().await` завершится сам, когда все отправители освобождены, — правило из статьи 24 никуда не делось.

## Типичные грабли

**Забытый `.await`.** Код собирается, задача не выполняется. Компилятор выдаёт лишь предупреждение об неиспользуемой переменной. Если асинхронный код «молча ничего не делает» — ищите пропущенный `.await` первым делом.

**Блокирующий вызов.** `std::thread::sleep`, синхронное чтение файла, тяжёлые вычисления останавливают весь поток рантайма. Лечится асинхронным аналогом или `spawn_blocking`.

**Последовательность вместо параллельности.** Цикл с `.await` внутри — самая незаметная потеря производительности:

```rust
for url in urls {
    results.push(fetch(url).await);      // строго по очереди
}
```

Правильно — собрать будущие и запустить вместе, через `join!` или `spawn`.

**Отмена в неподходящем месте.** Ветвь `select!` может быть прервана на любом `.await`. Операции, которые должны завершиться целиком, выносят в `spawn`: отдельная задача переживёт отмену `select!`.

**Границы `Send`.** Ошибка вида «future cannot be sent between threads safely» означает, что через `.await` живёт значение без `Send` — например, `Rc` или страж стандартного мьютекса. Лечится освобождением такого значения **до** `.await`: часто достаточно обернуть кусок кода в блок `{ }`.

## Что запомнить

- `join!` ждёт все задачи, `select!` — первую, отменяя остальные.
- Отменённая задача прерывается на `.await` и не завершает работу — не кладите в `select!` неразрывные операции.
- `timeout` ограничивает время будущего и возвращает `Result`; внешние вызовы стоит оборачивать всегда.
- Асинхронные `Mutex` и каналы приостанавливают задачу, а не блокируют поток.
- Для коротких критических секций без `.await` внутри обычный `std::sync::Mutex` лучше.
- Ограниченный канал даёт обратное давление; неограниченные опасны ростом памяти.
- `.await` в цикле выполняет задачи по очереди — параллельность требует `join!` или `spawn`.
- Ошибка про `Send` обычно означает, что `Rc` или страж мьютекса пережил `.await`.

## Практика

**1. Гонка задач.** Запустите три задачи с разным временем и через `select!` определите победителя. Повторите несколько раз с разными задержками. Готово, когда результат предсказуем по времени.

**2. Таймаут.** Оберните задачу на 500 мс в таймаут на 200 мс, затем на 800 мс. Обработайте оба исхода. Готово, когда программа корректно печатает и успех, и превышение.

**3. Цикл против параллельности.** Напишите функцию, обрабатывающую десять «запросов» по 100 мс. Сделайте две версии: цикл с `.await` и запуск через `join!`. Замерьте время. Готово, когда есть два числа около 1000 мс и около 100 мс.

**4. Обратное давление.** Создайте канал ёмкостью 2, быстрого производителя и медленного потребителя. Печатайте время каждой отправки. Готово, когда видно, что производитель притормаживает.

**5. Ловим `Send`.** Напишите асинхронную функцию, которая держит `Rc` через `.await`, и запустите её через `tokio::spawn`. Разберите ошибку. Почините двумя способами: заменой на `Arc` и сужением области жизни `Rc`. Готово, когда оба варианта собираются.
