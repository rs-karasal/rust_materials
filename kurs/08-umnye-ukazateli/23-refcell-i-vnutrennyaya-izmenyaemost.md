# 23. `RefCell`, внутренняя изменяемость и циклы ссылок

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

`Rc` из прошлой статьи дал разделяемое владение, но только для чтения. Между тем разделяемые данные обычно нужно менять. Разберём механизм, который это позволяет, — и его цену: часть проверок переезжает из компиляции в рантайм.

## Внутренняя изменяемость

Правило заимствования — либо много неизменяемых ссылок, либо одна изменяемая — проверяется компилятором. Проверка **консервативна**: компилятор отклоняет всё, в чём не уверен, включая код, который на самом деле безопасен.

`RefCell<T>` предлагает сделку: те же правила, но проверка **во время выполнения**. Снаружи значение выглядит неизменяемым, а внутри его можно менять — отсюда название «внутренняя изменяемость».

Доступ идёт через два метода:

- `borrow()` — неизменяемое заимствование;
- `borrow_mut()` — изменяемое.

`RefCell` считает активные заимствования. Нарушили правило — паника:

```rust
let c = RefCell::new(5);
let a = c.borrow_mut();
let b = c.borrow_mut();
```

```
thread 'main' panicked at pn.rs:5:15:
RefCell already borrowed
```

Тот же код с обычными ссылками не собрался бы вовсе. Здесь он собирается и падает при запуске — вот она, цена.

Сравним три способа хранить данные:

- **`T` и `&T`** — проверка при компиляции, один владелец, изменение по правилам заимствования.
- **`Rc<T>`** — проверка при компиляции, несколько владельцев, изменять нельзя.
- **`RefCell<T>`** — проверка **при выполнении**, один владелец, изменение изнутри.
- **`Rc<RefCell<T>>`** — проверка при выполнении, несколько владельцев, изменение возможно.

## `Rc<RefCell<T>>`

Комбинация двух типов даёт то, чего нет по отдельности: несколько владельцев, и все могут менять данные.

```rust
let shared = Rc::new(RefCell::new(vec![1, 2, 3]));
let clone = Rc::clone(&shared);

clone.borrow_mut().push(4);
println!("{:?}", shared.borrow());     // [1, 2, 3, 4]
```

Изменили через один указатель — увидели через другой. Это стандартная связка для разделяемого изменяемого состояния в однопоточном коде: графы, деревья с обратными ссылками, взаимные подписки.

Когда её применять? Только когда структура данных действительно требует нескольких владельцев. Если можно обойтись обычным владением и `&mut` — обходитесь: компилятор проверяет надёжнее рантайма.

## Циклы ссылок и утечки

У `Rc` есть слабое место. Rust гарантирует безопасность памяти, но **не** гарантирует отсутствие утечек — и `Rc` позволяет их устроить.

Пусть два узла ссылаются друг на друга через `Rc`. Счётчик каждого никогда не дойдёт до нуля: первый жив, потому что на него ссылается второй, и наоборот. Оба останутся в памяти навсегда, даже когда снаружи о них забудут.

Решение — **слабые ссылки** `Weak<T>`. Они не считаются владением: `Weak` не увеличивает `strong_count` и не удерживает данные от освобождения.

Поскольку данные могут исчезнуть, `Weak` не даёт к ним прямого доступа. Сначала — попытка «повысить» ссылку:

```rust
leaf.parent.borrow().upgrade()      // Option<Rc<Node>>
```

`upgrade` возвращает `Some(Rc)`, если данные живы, и `None`, если уже освобождены. Проверку не обойти — компилятор заставит её обработать.

## Дерево с родителями

Классический пример, где нужно всё сразу:

```rust
struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,        // слабая ссылка наверх
    children: RefCell<Vec<Rc<Node>>>,   // сильные ссылки вниз
}
```

Разберём типы по частям. `RefCell` — потому что связи меняются после создания узла. `Rc` для детей — родитель ими владеет. `Weak` для родителя — ребёнок родителем **не** владеет; будь там `Rc`, получился бы цикл.

```rust
let leaf = Rc::new(Node { value: 3, /* ... */ });
println!("{:?}", leaf.parent.borrow().upgrade().map(|n| n.value));   // None

let branch = Rc::new(Node {
    value: 5,
    children: RefCell::new(vec![Rc::clone(&leaf)]),
    /* ... */
});
*leaf.parent.borrow_mut() = Rc::downgrade(&branch);

println!("{:?}", leaf.parent.borrow().upgrade().map(|n| n.value));   // Some(5)
```

`Rc::downgrade` создаёт `Weak` из `Rc`. Счётчики показывают устройство связи:

```
branch strong=1 weak=1
leaf   strong=2 weak=0
```

У `branch` одна сильная ссылка (переменная) и одна слабая (от ребёнка). У `leaf` — две сильных: переменная и запись в `children`.

Правило, которое стоит запомнить: **владение идёт вниз, обратные ссылки — слабые**. Оно применимо к любым структурам с двусторонними связями.

## Что запомнить

- Проверка заимствований компилятором консервативна: часть безопасного кода она отклоняет.
- `RefCell<T>` переносит ту же проверку в рантайм; нарушение вызывает панику, а не ошибку сборки.
- `borrow()` и `borrow_mut()` — доступ к содержимому; активные заимствования считаются.
- `Rc<RefCell<T>>` даёт нескольких владельцев с правом изменения — стандартная связка для графов и деревьев.
- Rust не защищает от утечек: взаимные `Rc` образуют цикл, который никогда не освободится.
- `Weak<T>` ссылается, не владея; `Rc::downgrade` создаёт его, `upgrade` возвращает `Option<Rc<T>>`.
- В двусторонних связях владение направляют вниз, а обратные ссылки делают слабыми.

## Практика

**1. Первая паника.** Воспроизведите `RefCell already borrowed`. Затем почините код так, чтобы оба заимствования существовали, но не одновременно. Готово, когда программа работает и вы понимаете, что изменилось.

**2. Разделяемый счётчик.** Создайте `Rc<RefCell<i32>>`, сделайте три клона, увеличьте значение через каждый. Выведите итог через исходную переменную. Готово, когда счётчик равен трём.

**3. Компиляция против рантайма.** Напишите две версии одного кода: с `&mut` и с `RefCell`. В обеих намеренно нарушьте правило заимствования. Готово, когда есть таблица «версия → когда обнаружена ошибка → что произошло».

**4. Утечка своими руками.** Постройте два узла, ссылающихся друг на друга через `Rc`, добавьте им `Drop` с печатью. Убедитесь, что сообщения не появляются. Готово, когда утечка видна экспериментально.

**5. Дерево с родителями.** Постройте дерево из трёх узлов: корень и два ребёнка, с обратными ссылками через `Weak`. Печатайте `strong_count` и `weak_count` на каждом шаге. Проверьте, что `Drop` срабатывает. Готово, когда все узлы освобождаются и счётчики объяснимы.
