# 25. `Arc`, `Mutex`, `Send` и `Sync`

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Каналы из прошлой статьи хороши, когда данные передают. Но бывает состояние, действительно общее для всех потоков: счётчик обработанных запросов, кэш, реестр подключений. Разберём, как разделять память безопасно, и увидим два трейта, на которых держится вся многопоточность Rust.

## `Mutex<T>` — данные под замком

Мьютекс (mutual exclusion) пускает к данным только один поток одновременно. В Rust он устроен изящнее, чем в большинстве языков: **данные лежат внутри мьютекса**, и добраться до них можно только через замок.

```rust
let m = Mutex::new(0);
{
    let mut num = m.lock().unwrap();
    *num += 1;
}
```

`lock()` ждёт освобождения замка и возвращает `Result` — потому что поток, державший мьютекс, мог паникнуть, и замок оказался бы «отравлен».

Дальше самое интересное. `lock` отдаёт не значение, а **страж** (guard) — умный указатель, реализующий `Deref` (отсюда `*num`) и `Drop`. Когда страж выходит из области видимости, замок освобождается **автоматически**.

Сравните с языками, где `lock` и `unlock` вызывают вручную: там забытый `unlock` — обычное дело, и он подвешивает программу навсегда. Здесь забыть невозможно, о разблокировке заботится система владения.

## `Arc<T>` — счётчик ссылок для потоков

Чтобы мьютекс был доступен нескольким потокам, им нужно совместное владение. Знакомый `Rc` не подойдёт:

```rust
// ❌ не компилируется
let d = Rc::new(5);
let d2 = Rc::clone(&d);
thread::spawn(move || println!("{d2}"));
```

```
error[E0277]: `Rc<i32>` cannot be sent between threads safely
    |
    = help: within this closure, the trait `Send` is not implemented for `Rc<i32>`
```

`Rc` обновляет счётчик обычными операциями, без синхронизации: два потока могут увеличить его одновременно и потерять одно из увеличений — а дальше двойное освобождение.

`Arc` (atomically reference counted) делает то же самое атомарными операциями. Интерфейс идентичен:

```rust
let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..10 {
    let counter = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        let mut num = counter.lock().unwrap();
        *num += 1;
    }));
}

for h in handles { h.join().unwrap(); }
println!("итог: {}", *counter.lock().unwrap());     // 10
```

Десять потоков, никаких гонок, результат всегда 10.

Почему тогда не использовать `Arc` всегда? Атомарные операции дороже обычных. В однопоточном коде берите `Rc`, в многопоточном — `Arc`. Компилятор не даст ошибиться.

Заметьте параллель с прошлой статьёй: `Rc<RefCell<T>>` для одного потока и `Arc<Mutex<T>>` для нескольких — это одна и та же конструкция «общее владение плюс изменяемость», в двух вариантах.

## `RwLock<T>` — много читателей

Мьютекс пускает по одному даже тех, кто только читает. Если чтений намного больше, чем записей, подойдёт `RwLock`:

```rust
let data = Arc::new(RwLock::new(vec![1, 2, 3]));

{
    let r1 = data.read().unwrap();
    let r2 = data.read().unwrap();      // одновременно — можно
    println!("{:?} {:?}", *r1, *r2);
}

data.write().unwrap().push(4);          // эксклюзивно
```

Правило то же самое, что у ссылок: много читателей **либо** один писатель. Знакомая формулировка — правило заимствования из статьи 7, только проверяемое в рантайме.

## `Send` и `Sync`

Откуда компилятор вообще знает, что `Rc` нельзя отправить в поток? Из двух трейтов-маркеров:

- **`Send`** — значение можно **переместить** в другой поток.
- **`Sync`** — на значение можно **ссылаться** из нескольких потоков одновременно (то есть `&T` является `Send`).

У них нет методов, они ничего не делают — только помечают свойство типа. Почти все типы их реализуют, и делается это автоматически: если все поля структуры `Send`, структура тоже `Send`.

Исключения наперечёт:

- **`Rc<T>`** — не `Send` и не `Sync`: счётчик ссылок неатомарный.
- **`RefCell<T>`** — `Send`, но не `Sync`: неатомарный счётчик заимствований.
- **`Arc<T>`** — и `Send`, и `Sync`: счётчик атомарный.
- **`Mutex<T>`** — и `Send`, и `Sync`: для того и создан.

Именно эти трейты превращают правила многопоточности в проверку типов. Не нужно помнить, какие структуры безопасны: попытка отправить неподходящий тип в поток просто не компилируется — как мы только что видели.

## Взаимоблокировки

Одну вещь Rust **не** предотвращает: deadlock. Два потока, каждый держит один мьютекс и ждёт второй, — программа зависает навсегда. Ошибки типов здесь нет, и компилятору не за что зацепиться.

Правила, которые с этим помогают:

- захватывайте мьютексы **всегда в одном порядке**;
- держите замок как можно короче — вычисляйте снаружи, под замком только присваивайте;
- не вызывайте под замком чужой код, который может захотеть тот же замок;
- по возможности предпочитайте каналы.

## Что запомнить

- `Mutex<T>` хранит данные внутри себя: добраться до них можно только через `lock()`.
- `lock()` возвращает страж, освобождающий замок автоматически при выходе из области видимости.
- `Rc` в потоках не работает — счётчик неатомарный; для многопоточности есть `Arc`.
- `Arc` дороже `Rc`, поэтому в однопоточном коде используют `Rc`.
- `Arc<Mutex<T>>` — многопоточный аналог `Rc<RefCell<T>>`.
- `RwLock` пускает много читателей либо одного писателя — правило заимствования в рантайме.
- `Send` — можно переместить в другой поток, `Sync` — можно разделять по ссылке; реализуются автоматически.
- От взаимоблокировок Rust не защищает: порядок захвата замков — на вашей совести.

## Практика

**1. Гонка, которой не будет.** Запустите 100 потоков, увеличивающих общий счётчик. Проверьте, что итог ровно 100 при нескольких запусках. Готово, когда результат стабилен.

**2. Ловим `Send`.** Попробуйте передать `Rc` в поток и разберите ошибку. Замените на `Arc`. Готово, когда можете объяснить, чем именно опасен `Rc` между потоками.

**3. Страж и область видимости.** Напишите код, где замок захвачен в длинном блоке, и добавьте туда `println!` с попыткой захватить его повторно. Получите зависание. Затем сократите область стража. Готово, когда программа перестала виснуть.

**4. `RwLock` против `Mutex`.** Реализуйте общий кэш: восемь потоков читают, два пишут. Сделайте две версии — на `Mutex` и на `RwLock` — и замерьте время. Готово, когда есть два числа и объяснение разницы.

**5. Взаимоблокировка своими руками.** Создайте два мьютекса и два потока, захватывающих их в противоположном порядке. Добейтесь зависания, затем почините единым порядком захвата. Готово, когда обе версии воспроизводятся осознанно.
