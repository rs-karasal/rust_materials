# 24. Потоки и каналы `mpsc`

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Многопоточность обычно считают самой опасной частью программирования: гонки данных проявляются случайно, воспроизводятся плохо и живут в проде месяцами. В Rust большинство таких ошибок просто не компилируется — правила владения, которые мешали нам первые недели, здесь окупаются целиком. Термин «бесстрашная многопоточность» (fearless concurrency) — как раз про это.

## Создание потока

```rust
use std::thread;

let handle = thread::spawn(|| {
    for i in 1..4 {
        println!("поток: {i}");
    }
    42
});
```

`thread::spawn` принимает замыкание и запускает его в новом потоке операционной системы. Возвращает **дескриптор** (handle), через который можно дождаться завершения:

```rust
let result = handle.join().unwrap();
println!("поток вернул {result}");      // 42
```

`join` блокирует текущий поток до окончания дочернего и отдаёт возвращённое значение. `unwrap` нужен, потому что поток мог паниковать — тогда `join` вернёт `Err`.

Без `join` главный поток может завершиться первым, и остальные будут убиты на середине. Место вызова `join` определяет, работают потоки параллельно или последовательно: поставите его сразу после `spawn` — параллельности не будет.

## Захват данных

Замыкание в потоке подчиняется правилам из статьи 19, но с дополнительным требованием:

```rust
// ❌ не компилируется
let v = vec![1, 2, 3];
let h = thread::spawn(|| println!("{v:?}"));
```

```
error[E0373]: closure may outlive the current function, but it borrows `v`,
              which is owned by the current function
  |
note: function requires argument type to outlive `'static`
help: to force the closure to take ownership of `v` (and any other referenced
      variables), use the `move` keyword
```

Компилятор рассуждает так: новый поток может пережить функцию, где создан. Значит, ссылка на локальную переменную станет висячей. Обычные ссылки в поток передать нельзя — только владение:

```rust
let data = vec![1, 2, 3];
let h = thread::spawn(move || {
    println!("захватили {data:?}");
});
```

Обратите внимание, что произошло. В большинстве языков этот код прекрасно скомпилировался бы и упал в рантайме — на определённом расписании потоков, у одного пользователя из тысячи. Здесь ошибка возникла при сборке, и компилятор сразу назвал решение.

## Каналы

Второй способ работы с потоками — не разделять данные, а **передавать сообщения**. Философия, знакомая по Go: «не общайтесь, разделяя память; разделяйте память, общаясь».

```rust
use std::sync::mpsc;

let (tx, rx) = mpsc::channel();
```

`mpsc` — multiple producer, single consumer: отправителей может быть много, получатель один. `tx` (transmitter) отправляет, `rx` (receiver) принимает.

```rust
for id in 0..3 {
    let tx = tx.clone();
    thread::spawn(move || {
        tx.send(format!("сообщение от {id}")).unwrap();
    });
}
drop(tx);

for msg in rx {
    println!("{msg}");
}
```

Разберём важные детали.

**`tx.clone()`** — каждому потоку нужен свой отправитель, потому что `move` забирает владение. Клонирование отправителя как раз для этого и предусмотрено.

**`send` забирает владение** значением. После отправки использовать его нельзя — данные физически переехали в другой поток, и правило одного владельца это гарантирует. Именно поэтому каналы в Rust безопасны без всяких договорённостей.

**`drop(tx)`** — обязательный шаг, о котором забывают. Получатель понимает, что данных больше не будет, когда закрыты **все** отправители. Исходный `tx` остался в главном потоке; не освободив его, вы получите вечное ожидание.

**Получатель как итератор.** `for msg in rx` — цикл, который выдаёт сообщения по мере поступления и завершается при закрытии канала. Есть и явные методы: `recv()` блокирует до сообщения, `try_recv()` возвращает результат сразу.

## Какой способ выбрать

- **Модель.** Каналы — передача сообщений; разделяемое состояние — общая память под замком.
- **Владение.** С каналами оно переходит вместе с данными, с общим состоянием — разделяется.
- **Когда удобно.** Каналы — конвейер и раздача заданий рабочим потокам; общее состояние — счётчик, кэш, реестр.
- **Риск взаимоблокировки.** У каналов низкий, у общего состояния есть.

**Начинайте с каналов.** Они естественно ложатся на систему владения и почти не оставляют места для ошибок. Разделяемое состояние берите, когда данные действительно общие, — этим займёмся в следующей статье.

## Что запомнить

- `thread::spawn` запускает замыкание в новом потоке ОС и возвращает дескриптор.
- `join()` ждёт завершения и отдаёт результат; без него потоки могут быть убиты вместе с `main`.
- Место вызова `join` определяет, будет ли реальная параллельность.
- В поток нельзя передать обычную ссылку — только владение через `move`.
- Гонки данных и висячие ссылки в потоках ловятся при компиляции, а не в проде.
- `mpsc::channel` даёт пару «отправитель — получатель»; отправителей можно клонировать.
- `send` забирает владение значением — данные не остаются в двух местах.
- Пока не закрыты все отправители, получатель ждёт; лишний `tx` нужно освободить через `drop`.

## Практика

**1. Первый поток.** Запустите поток, печатающий числа от 1 до 5, параллельно печатайте буквы в главном. Затем переставьте `join` сразу после `spawn` и сравните вывод. Готово, когда видите разницу между параллельным и последовательным исполнением.

**2. Ловим `E0373`.** Попробуйте передать в поток вектор без `move`. Разберите ошибку и почините. Затем попробуйте использовать вектор после запуска потока. Готово, когда понимаете обе ошибки.

**3. Результат из потока.** Запустите три потока, каждый считает сумму своей части большого вектора. Соберите результаты через `join` и сложите. Готово, когда итог совпадает с однопоточным подсчётом.

**4. Канал.** Запустите поток, отправляющий пять сообщений с паузой в 100 мс. В главном потоке принимайте их циклом. Готово, когда сообщения появляются постепенно, а не все сразу.

**5. Несколько отправителей.** Запустите четыре потока-производителя, каждый шлёт по три сообщения со своим номером. Соберите все двенадцать. Затем уберите `drop(tx)` и посмотрите, что произойдёт. Готово, когда можете объяснить зависание.
