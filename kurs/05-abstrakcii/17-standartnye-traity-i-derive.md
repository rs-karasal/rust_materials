# 17. Стандартные трейты и `derive`

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

В Rust почти всё привычное поведение — печать, сравнение, копирование, преобразование типов — описано трейтами из стандартной библиотеки. Пока ваш тип их не реализует, он не умеет ничего: даже сравнить две структуры на равенство не выйдет. Хорошая новость: большинство реализаций компилятор напишет за вас.

## Почему структура «ничего не умеет»

```rust
// ❌ не компилируется
struct P { x: f64 }
let a = P { x: 1.0 };
let b = P { x: 1.0 };
println!("{}", a == b);
```

```
error[E0369]: binary operation `==` cannot be applied to type `P`
  |
note: an implementation of `PartialEq` might be missing for `P`
```

Оператор `==` — это не встроенная возможность языка, а вызов метода трейта `PartialEq`. Нет реализации — нет оператора. Так устроены все операторы: `+` — это `Add`, `<` — `PartialOrd`, `[]` — `Index`.

## `derive`: реализации автоматом

Для типовых случаев компилятор генерирует реализацию сам:

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Default)]
struct Version {
    major: u32,
    minor: u32,
}
```

Одна строка — и структура умеет печататься, копироваться, сравниваться, сортироваться и служить ключом в `HashMap`.

Что даёт каждый:

| Трейт | Что появляется | Условие |
|---|---|---|
| `Debug` | вывод через `{:?}` и `{:#?}` | все поля `Debug` |
| `Clone` | метод `.clone()` | все поля `Clone` |
| `Copy` | копирование вместо перемещения | все поля `Copy`, требует `Clone` |
| `PartialEq` | операторы `==` и `!=` | все поля `PartialEq` |
| `Eq` | маркер полного равенства | требует `PartialEq` |
| `PartialOrd` | `<`, `>`, `<=`, `>=` | требует `PartialEq` |
| `Ord` | полная упорядоченность, `.sort()` | требует `Eq` и `PartialOrd` |
| `Hash` | использование как ключа в `HashMap` | все поля `Hash` |
| `Default` | `Type::default()` | все поля `Default` |

Сгенерированные реализации работают **по полям**: сравнение проверяет поля по очереди, сортировка идёт по порядку объявления. Отсюда практический вывод — **порядок полей влияет на сортировку**:

```rust
let mut list = vec![b, a, Version::default()];
list.sort();
// [Version { major: 0, minor: 0 }, Version { major: 1, minor: 2 }, Version { major: 1, minor: 10 }]
```

Сначала по `major`, при равенстве — по `minor`. Ровно то, что нужно для версий, и это не случайность, а следствие порядка полей.

Пара `PartialEq` / `Eq` кажется избыточной, но различие содержательное. `Eq` требует, чтобы значение всегда равнялось само себе. Для `f64` это неверно: `NaN != NaN`. Поэтому числа с плавающей точкой реализуют только `PartialEq`, и структура с полем `f64` не может получить `Eq` и `Ord`.

## `Display` — вывод для человека

Единственный из основных трейтов, который **нельзя** вывести автоматически: компилятор не знает, как ваш тип должен выглядеть для пользователя.

```rust
use std::fmt;

impl fmt::Display for Version {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "v{}.{}", self.major, self.minor)
    }
}

println!("{a}");     // v1.2
```

`write!` работает как `println!`, но пишет в переданный форматтер.

Разделение труда простое: **`Debug` — для разработчика** (структура со всеми полями, `{:?}`), **`Display` — для пользователя** (`{}`). `Debug` ставят почти всем типам, `Display` — только тем, что действительно показывают наружу.

Бонусом: реализовав `Display`, вы бесплатно получаете метод `.to_string()`.

## `From` и `Into` — преобразования

`From` описывает превращение одного типа в другой:

```rust
struct Celsius(f64);
struct Fahrenheit(f64);

impl From<Celsius> for Fahrenheit {
    fn from(c: Celsius) -> Self {
        Fahrenheit(c.0 * 9.0 / 5.0 + 32.0)
    }
}
```

Главная выгода — **`Into` появляется автоматически**. Реализовали одно направление, получили два способа вызова:

```rust
let f = Fahrenheit::from(Celsius(0.0));       // явно
let f: Fahrenheit = Celsius(100.0).into();    // через тип переменной
```

Правило: **реализуйте `From`, никогда не реализуйте `Into` руками**.

Эти трейты вы уже встречали, не зная имён: `String::from("...")`, `i64::from(42i32)`, а главное — преобразование ошибок оператором `?` из статьи 14. Всё это одна и та же пара.

Для преобразований, которые могут не удаться, есть `TryFrom` / `TryInto` — они возвращают `Result`. Например, `u8::try_from(300i32)` даст ошибку, потому что число не влезает.

`Default` тоже стоит запомнить отдельно: он даёт «нулевое» значение (`Version::default()` — все поля по умолчанию) и позволяет писать `..Default::default()` в синтаксисе обновления структуры из статьи 9.

## Что запомнить

- Операторы в Rust — это методы трейтов; без реализации тип не умеет ни сравниваться, ни складываться.
- `#[derive(...)]` генерирует реализации по полям для `Debug`, `Clone`, `Copy`, `PartialEq`, `Eq`, `PartialOrd`, `Ord`, `Hash`, `Default`.
- Порядок полей определяет порядок сортировки при `derive(Ord)`.
- `Eq` требует, чтобы значение равнялось само себе, — с `f64` он невозможен.
- `Display` пишется вручную: `Debug` для разработчика, `Display` для пользователя.
- Реализация `Display` бесплатно даёт `.to_string()`.
- Реализуйте `From` — `Into` появится сам. Для ненадёжных преобразований есть `TryFrom`.

## Практика

**1. Минимальный набор.** Опишите структуру `Point { x: i32, y: i32 }` и попробуйте её напечатать, сравнить и клонировать без единого `derive`. Соберите коды ошибок. Затем добавьте нужные трейты. Готово, когда есть таблица «операция → трейт».

**2. Порядок полей и сортировка.** Опишите `Employee` с полями «отдел» и «имя», выведите `Ord`, отсортируйте вектор. Затем поменяйте поля местами и снова отсортируйте. Готово, когда объяснили разницу в результате.

**3. `Eq` и `f64`.** Попробуйте вывести `Eq` и `Ord` для структуры с полем `f64`. Разберите ошибку. Готово, когда можете объяснить, при чём тут `NaN`.

**4. `Display` своими руками.** Реализуйте `Display` для структуры «денежная сумма» так, чтобы она печаталась как `1 500,00 ₸`. Проверьте, что заработал `.to_string()`. Готово, когда оба способа вывода дают одинаковый текст.

**5. `From` в обе стороны.** Опишите `Meters` и `Feet`, реализуйте `From` в обе стороны. Вызовите преобразования четырьмя способами: `from` и `into` для каждого направления. Готово, когда ни одной реализации `Into` вы не написали.
