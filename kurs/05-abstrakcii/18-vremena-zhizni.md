# 18. Времена жизни: `'a` и элизия

> ⏱ **~55 минут** · теория 25 мин · практика 30 мин

Странные апострофы в сигнатурах — то, что отпугивает в чужом коде на Rust сильнее всего. На деле идея простая, и вы уже пользуетесь ею с седьмой статьи: компилятор следит, чтобы ссылка не пережила данные. Времена жизни — просто способ объяснить ему это в тех случаях, когда он не может догадаться сам.

## Зачем они нужны

Напишем функцию, возвращающую более длинную из двух строк:

```rust
// ❌ не компилируется
fn longest(x: &str, y: &str) -> &str {
    if x.len() > y.len() { x } else { y }
}
```

```
error[E0106]: missing lifetime specifier
 --> l1.rs:1:33
  |
1 | fn longest(x: &str, y: &str) -> &str {
  |               ----     ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but the
    signature does not say whether it is borrowed from `x` or `y`
```

Компилятор объясняет проблему точно. Он проверяет каждую функцию **по отдельности**, не заглядывая в тело. Из сигнатуры не видно, какую из двух ссылок вернут, — а значит, непонятно, сколько результат должен прожить.

Это не придирка. Пока вызывающий код не знает связи между аргументами и результатом, он не может гарантировать, что не получит ссылку на уже освобождённые данные.

## Аннотации

Решение — назвать время жизни и связать им параметры и результат:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

`'a` — параметр времени жизни, объявляется рядом с обобщёнными типами. Читается это так: «обе входные ссылки живут хотя бы `'a`, и результат живёт столько же».

Самое важное про аннотации: **они ничего не меняют**. Ни одна ссылка от них не станет жить дольше или короче. Это только описание уже существующих связей — как аннотация типа не превращает число в строку, а лишь сообщает компилятору то, что и так верно.

На практике `'a` становится **меньшим** из времён жизни аргументов: результат безопасен настолько, насколько безопасен самый короткоживущий из них.

Проверим:

```rust
// ❌ не компилируется
let s1 = String::from("длинная");
let result;
{
    let s2 = String::from("коротко");
    result = longest(s1.as_str(), s2.as_str());
}
println!("{result}");
```

```
error[E0597]: `s2` does not live long enough
   |
 8 |         let s2 = String::from("коротко");
   |             -- binding `s2` declared here
 9 |         result = longest(s1.as_str(), s2.as_str());
   |                                       ^^ borrowed value does not live long enough
10 |     }
   |     - `s2` dropped here while still borrowed
11 |     println!("{result}");
   |                ------ borrow later used here
```

Компилятор восстановил всю цепочку: `s2` умерла на закрывающей скобке, а `result` мог указывать на неё. Заметьте — он не рассуждал о том, какая строка на самом деле длиннее. Проверка идёт по сигнатуре, а не по поведению программы.

Если перенести `println!` внутрь блока, код скомпилируется: там `s2` ещё жива.

## Элизия: почему обычно их не пишут

Возникает вопрос: раньше-то ссылки возвращались без всяких `'a`.

```rust
fn first_word(s: &str) -> &str {
    s.split(' ').next().unwrap()
}
```

Времена жизни здесь есть — они просто не написаны. Компилятор расставляет их сам по трём правилам **элизии**:

1. Каждый параметр-ссылка получает собственное время жизни.
2. Если входной параметр ровно один, его время жизни присваивается всем выходным ссылкам.
3. Если параметров несколько, но один из них `&self` или `&mut self`, всем выходным ссылкам присваивается время жизни `self`.

Для `first_word` сработало правило 2: параметр один, возвращать можно только его данные. Для `longest` — два параметра, ни один не `self`, правила не помогли, и компилятор потребовал аннотацию.

Третье правило особенно ценно: благодаря ему методы почти никогда не требуют аннотаций, хотя постоянно возвращают ссылки на поля.

**Практический вывод: пишите без аннотаций, пока компилятор не попросит.** Он попросит редко.

## Времена жизни в структурах

Структура может хранить ссылку — но тогда обязана объявить время жизни:

```rust
struct Excerpt<'a> {
    part: &'a str,
}
```

Смысл: «экземпляр `Excerpt` не может пережить строку, на которую ссылается `part`».

```rust
let novel = String::from("Зовите меня Измаил. Прошло несколько лет.");
let first = novel.split('.').next().unwrap();
let e = Excerpt { part: first };
```

Пока жив `novel`, всё в порядке. Освободите его раньше — компилятор не даст использовать `e`.

В блоке `impl` параметр объявляют дважды, как и обобщённый тип:

```rust
impl<'a> Excerpt<'a> {
    fn announce(&self, msg: &str) -> &str {
        println!("Внимание: {msg}");
        self.part
    }
}
```

Внутри метода аннотации не понадобились — сработало третье правило элизии.

Отсюда совет из статьи 9: **на старте храните в структурах владеющие типы** (`String`), а не ссылки. Ссылки в полях оправданы, когда важно избежать копирования, и стоят они усложнением всего, что структуру касается.

## `'static`

Особое время жизни — «живёт всю программу»:

```rust
let s: &'static str = "живу всю программу";
```

Все строковые литералы имеют `'static`: они лежат в бинарнике и никогда не освобождаются.

Осторожно с советом компилятора добавить `'static` при ошибке — это почти всегда лечение симптома. Обычно проблема в том, что данные живут недостаточно долго, и правильный ответ — вернуть владеющий тип, а не растягивать время жизни ссылки.

## Что запомнить

- Времена жизни — способ объяснить компилятору связь между временем жизни аргументов и результата.
- Компилятор анализирует каждую функцию по сигнатуре, не заглядывая в тело, — поэтому связь нужно объявить.
- Аннотации ничего не меняют: они описывают существующие ограничения, а не создают новые.
- `'a` на практике — меньшее из времён жизни аргументов.
- Три правила элизии избавляют от аннотаций в большинстве случаев, особенно в методах (`&self`).
- Структура, хранящая ссылку, обязана объявить время жизни и не может пережить свои данные.
- `'static` — на всю программу; таковы строковые литералы. Добавлять его по подсказке компилятора обычно неправильно.

## Практика

**1. Ловим `E0106`.** Напишите функцию, возвращающую более короткую из двух строк, без аннотаций. Разберите ошибку, затем добавьте `'a`. Готово, когда понимаете, чего именно не хватало компилятору.

**2. Ссылка переживает данные.** Воспроизведите ошибку `E0597` с вложенным блоком. Затем почините её двумя способами: перенеся использование внутрь блока и вернув `String` вместо `&str`. Готово, когда оба варианта собираются.

**3. Правила элизии.** Для четырёх сигнатур определите **до** проверки, нужна ли аннотация: `fn f(s: &str) -> &str`, `fn g(a: &str, b: &str) -> &str`, `fn h(&self, x: &str) -> &str`, `fn i(a: &str, b: &str) -> String`. Затем проверьте компилятором. Готово, когда все четыре предсказания подтвердились.

**4. Структура со ссылкой.** Опишите `Parser<'a>` с полем `input: &'a str` и методом, возвращающим первое слово. Создайте парсер от `String` и попробуйте использовать его после освобождения строки. Готово, когда компилятор поймал ошибку.

**5. Владение вместо ссылок.** Перепишите `Parser` так, чтобы он владел строкой. Сравните два варианта: где меньше аннотаций, где меньше копирований. Готово, когда можете назвать ситуацию, в которой уместен каждый.

3. Меняет ли аннотация `'a` реальное время жизни данных?
4. Каким оказывается `'a`, если аргументы живут разное время?
5. Сформулируйте три правила элизии. Какое из них избавляет методы от аннотаций?
