# 6. Стек, куча и владение: три правила Rust

> ⏱ **~60 минут** · теория 25 мин · практика 35 мин

Мы подошли к главной идее языка. Владение (ownership) — это то, ради чего Rust вообще существует: механизм, позволяющий обойтись без сборщика мусора и при этом не давать программисту выстрелить себе в ногу. Тема непривычная, поэтому не торопитесь: эту статью лучше прочитать дважды, чем пройти дальше наполовину понятой.

## Стек и куча

Чтобы понять владение, нужно знать, где вообще лежат данные.

**Стек** работает по принципу стопки тарелок: положили сверху — сняли сверху. Он очень быстрый, потому что место всегда известно — конец стопки. Но у стека жёсткое требование: **размер данных должен быть известен на этапе компиляции**. Все типы из статьи 4 — числа, `bool`, `char`, массивы фиксированной длины — живут на стеке.

**Куча** (heap) устроена сложнее. Когда размер заранее неизвестен или данные должны пережить текущую функцию, программа просит у аллокатора участок памяти нужного объёма и получает указатель на него. Это медленнее: аллокатору нужно найти подходящее место, а потом обращаться к данным придётся через указатель.

Классический пример типа, живущего в куче, — строка `String`: она умеет расти, а значит, её размер при компиляции неизвестен.

Именно управление кучей — источник большинства ошибок в C и C++: забыли освободить память (утечка), освободили дважды, обратились к освобождённому участку. **Владение — это набор правил, по которым Rust решает, когда освобождать память в куче.** Проверяются они при компиляции и ничего не стоят во время работы программы.

## Три правила

Всё владение умещается в три пункта:

1. У каждого значения есть **владелец** — переменная.
2. Владелец в каждый момент времени **ровно один**.
3. Когда владелец выходит из области видимости, значение **освобождается**.

Третье правило проще всего увидеть на примере. Возьмём тип, который печатает сообщение при освобождении:

```rust
fn main() {
    {
        let _n = Noisy;
        println!("внутри блока");
    }
    println!("после блока");
}
```

```
внутри блока
Noisy освобождён
после блока
```

Память освободилась ровно на закрывающей скобке — не раньше и не позже. Никакой сборщик мусора не решал, когда это сделать: момент известен компилятору заранее, и он просто вставил вызов освобождения в нужное место.

## Перемещение

Теперь второе правило — то самое, из-за которого новички спорят с компилятором. Посмотрите на код, который в любом другом языке был бы совершенно безобиден:

```rust
// ❌ не компилируется
fn main() {
    let s1 = String::from("привет");
    let s2 = s1;
    println!("{s1}");
}
```

```
error[E0382]: borrow of moved value: `s1`
 --> m1.rs:4:16
  |
2 |     let s1 = String::from("привет");
  |         -- move occurs because `s1` has type `String`, which does not implement the `Copy` trait
3 |     let s2 = s1;
  |              -- value moved here
4 |     println!("{s1}");
  |                ^^ value borrowed here after move
  |
help: consider cloning the value if the performance cost is acceptable
  |
3 |     let s2 = s1.clone();
  |                ++++++++
```

Что произошло? `String` состоит из двух частей: на стеке лежит «шапка» (указатель на данные, длина, вместимость), а сами символы — в куче. При `let s2 = s1` копируется только шапка. Теперь две переменные указывают на один участок кучи.

И тут возникает проблема: когда обе выйдут из области видимости, каждая попытается освободить память — то самое **двойное освобождение**, классическая уязвимость C++.

Rust решает её радикально: `s1` объявляется **перемещённой** (moved) и больше не действует. Владелец остаётся один — `s2`. Не «поверхностное копирование», а именно перемещение: старая переменная становится непригодной.

То же самое происходит при передаче значения в функцию:

```rust
// ❌ не компилируется
fn takes(s: String) {
    println!("{s}");
}

fn main() {
    let s = String::from("привет");
    takes(s);
    println!("{s}");
}
```

```
error[E0382]: borrow of moved value: `s`
...
note: consider changing this parameter type in function `takes` to borrow instead if owning the value isn't necessary
```

Вызов функции забрал владение: строка «уехала» внутрь `takes` и была освобождена, когда та завершилась. Компилятор при этом намекает на правильное решение — «одолжить» вместо того, чтобы отбирать. Заимствованием займёмся в следующей статье.

## Копирование вместо перемещения

Но ведь это работает без всяких проблем:

```rust
let x = 5;
let y = x;
println!("{x} {y}");   // 5 5
```

Почему целое число не переместилось? Потому что оно целиком лежит на стеке, копируется одной машинной операцией и не владеет ничем в куче — освобождать нечего, двойного освобождения не бывает. Такие типы помечены особым трейтом **`Copy`**, и для них присваивание делает копию.

`Copy` реализуют:

- все числовые типы,
- `bool` и `char`,
- кортежи и массивы, **если все их элементы тоже `Copy`** (`(i32, i32)` — да, `(i32, String)` — нет).

Простое правило: **если тип владеет чем-то в куче, он не `Copy`**.

## Явное клонирование

Если данные из кучи действительно нужны в двух местах, копию запрашивают явно:

```rust
let s1 = String::from("привет");
let s2 = s1.clone();
println!("{s1} {s2}");   // обе живы
```

`clone()` выделяет новый участок кучи и копирует туда содержимое. Это может быть дорого — поэтому Rust и требует писать вызов руками. Философия языка: **дорогие операции должны быть видны в коде**.

Начинающие часто расставляют `.clone()` везде, где ругается компилятор. На старте это допустимо — программа будет работать. Но правильное решение почти всегда другое, и о нём — следующая статья.

## Что запомнить

- Стек быстрый и требует известного при компиляции размера; куча гибкая и медленнее.
- Владение — правила, по которым Rust решает, когда освободить память в куче. Всё проверяется при компиляции.
- Три правила: у значения есть владелец; владелец один; при выходе владельца из области видимости значение освобождается.
- Присваивание значения из кучи **перемещает** его: старая переменная перестаёт действовать.
- Передача в функцию тоже перемещает владение.
- Типы с трейтом `Copy` (числа, `bool`, `char`, кортежи из них) копируются, а не перемещаются, — им нечего освобождать.
- `clone()` делает настоящую копию данных в куче. Пишется явно, потому что стоит дорого.

## Практика

**1. Момент освобождения.** Возьмите пример с блоком из статьи и предскажите порядок вывода **до** запуска. Затем создайте две переменные в одной области видимости и определите, в каком порядке они освобождаются. Готово, когда предсказание совпало с выводом.

**2. Ловим перемещение.** Воспроизведите ошибку `E0382` со `String`. Прочитайте сообщение целиком и выпишите: где произошло перемещение, почему тип не `Copy`, что предлагает компилятор. Готово, когда можете объяснить ошибку своими словами.

**3. Copy или не Copy.** Проверьте экспериментально, какие из этих значений перемещаются, а какие копируются: `i32`, `bool`, `[i32; 3]`, `(i32, char)`, `String`, `(i32, String)`. Готово, когда у вас есть таблица из шести строк с ответом «переместилось / скопировалось» и объяснением почему.

**4. Функция забирает владение.** Напишите функцию `consume(s: String)`, которая печатает строку. Вызовите её дважды подряд с одной переменной. Объясните ошибку. Затем почините её через `clone()`. Готово, когда программа печатает строку дважды.

**5. Возврат владения.** Напишите функцию, которая принимает `String`, добавляет к ней восклицательный знак (подсказка: `push_str`, потребуется `mut`) и **возвращает** строку обратно. Вызовите её так, чтобы исходная переменная осталась доступна после вызова. Готово, когда программа печатает изменённую строку без единого `clone()`.
