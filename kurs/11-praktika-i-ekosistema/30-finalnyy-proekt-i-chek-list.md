# 30. Финальный проект и чек-лист Rust-джуна

> ⏱ **~6–10 часов** · теория 15 мин · проект 6–10 часов

Двадцать девять статей позади. Осталось собрать знания в одну работающую вещь: отдельные темы забываются, проект — нет. Ниже разбор архитектуры финального задания, чек-лист для самопроверки и ответ на вопрос «что учить дальше».

## Проект: менеджер задач

Утилита командной строки, хранящая задачи в JSON. Она выбрана не случайно: чтобы её написать, придётся задействовать почти каждую тему курса — от структур до трейтов, от `Result` до итераторов.

**Требования:**

- добавление, просмотр, изменение статуса и удаление задач;
- фильтрация по статусу, поиск по подстроке в названии;
- хранение в JSON-файле, путь настраивается флагом;
- внятные сообщения об ошибках, никаких `unwrap` в рабочем коде;
- тесты на бизнес-логику.

## Архитектура

Начните с типов — в Rust это самый естественный порядок.

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub enum Status {
    Todo,
    InProgress,
    Done,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Task {
    pub id: u32,
    pub title: String,
    pub status: Status,
}
```

Статус — перечисление, а не строка: невозможное состояние становится непредставимым, и `match` по нему исчерпывающий.

Дальше — свой тип ошибки (статья 14):

```rust
#[derive(Debug, Error)]
pub enum TaskError {
    #[error("задача {0} не найдена")]
    NotFound(u32),
    #[error("пустое название задачи")]
    EmptyTitle,
    #[error("ошибка хранилища")]
    Storage(#[from] std::io::Error),
}
```

Хранилище стоит спрятать за трейтом — тогда тесты смогут работать в памяти, без файлов:

```rust
pub trait Storage {
    fn load(&self) -> Result<Vec<Task>, TaskError>;
    fn save(&self, tasks: &[Task]) -> Result<(), TaskError>;
}
```

Бизнес-логика не знает, откуда берутся данные:

```rust
impl TaskList {
    pub fn add(&mut self, title: &str) -> Result<u32, TaskError> {
        if title.trim().is_empty() {
            return Err(TaskError::EmptyTitle);
        }
        let id = self.tasks.iter().map(|t| t.id).max().unwrap_or(0) + 1;
        self.tasks.push(Task { id, title: title.to_string(), status: Status::Todo });
        Ok(id)
    }

    pub fn complete(&mut self, id: u32) -> Result<(), TaskError> {
        let task = self.tasks.iter_mut()
            .find(|t| t.id == id)
            .ok_or(TaskError::NotFound(id))?;
        task.status = Status::Done;
        Ok(())
    }

    pub fn by_status(&self, status: Status) -> impl Iterator<Item = &Task> {
        self.tasks.iter().filter(move |t| t.status == status)
    }
}
```

В этих двадцати строках собрано полкурса: итераторы с `map`/`find`/`filter`, `ok_or` как мост от `Option` к `Result`, оператор `?`, возврат `impl Iterator`, заимствование `&mut self`.

**Раскладка по файлам:**

```
src/
├── main.rs        // разбор аргументов clap, вызовы, вывод
├── lib.rs         // публичный интерфейс
├── task.rs        // Task, Status
├── list.rs        // TaskList — бизнес-логика
├── storage.rs     // трейт Storage и реализация на JSON
└── error.rs       // TaskError
tests/
└── integration.rs
```

Логика в `lib.rs`, `main.rs` — тонкая оболочка. Иначе интеграционные тесты из статьи 21 к ней не подступятся.

**Порядок работы:** типы и ошибки → `TaskList` с тестами → хранилище → CLI. К моменту, когда дойдёте до `clap`, всё остальное уже проверено тестами.

## Чек-лист Rust-джуна

Отметьте, что можете объяснить и применить без подсказок.

**Владение**
- [ ] Объясняю разницу между перемещением, копированием и клонированием
- [ ] Понимаю, почему `String` перемещается, а `i32` — нет
- [ ] Читаю ошибки `E0382`, `E0499`, `E0502` и чиню их без `clone()`
- [ ] Понимаю, когда нужен `&`, когда `&mut`, когда владение

**Типы**
- [ ] Проектирую предметную область структурами и перечислениями
- [ ] Использую `Option` вместо «пустых» значений и `Result` вместо исключений
- [ ] Пишу `match` со стражами, `if let`, `let else`
- [ ] Понимаю, когда `derive` достаточно, а когда нужен ручной `impl`

**Абстракции**
- [ ] Пишу обобщённые функции и типы с ограничениями
- [ ] Объявляю и реализую трейты, выбираю между `impl Trait` и `dyn Trait`
- [ ] Понимаю, зачем нужны времена жизни, и не пугаюсь `'a`

**Практика**
- [ ] Организую проект по модулям и файлам
- [ ] Пишу юнит- и интеграционные тесты, документирую публичный интерфейс
- [ ] Обрабатываю ошибки через свой тип или `anyhow`, без `unwrap` в рабочем коде
- [ ] Читаю чужой код на Rust и документацию на docs.rs
- [ ] Использую `clippy` и понимаю его замечания

**Конкурентность** (для многих вакансий — плюс, а не требование)
- [ ] Запускаю потоки, передаю данные каналами
- [ ] Понимаю `Arc<Mutex<T>>` и различаю `Send` и `Sync`
- [ ] Пишу асинхронный код и знаю, чем `join!` отличается от последовательных `.await`

Если отмечено больше двух третей — вы джун. Оставшееся честнее добирать на реальных задачах, чем ещё одним прогоном теории.

## Что дальше

**Практика, а не новая теория.** Самая частая ошибка после курса — начать второй учебник. Пишите: свой инструмент, участие в open source, задачи на Exercism или Advent of Code.

**Читайте чужой код.** В Rust это особенно полезно: стандартная библиотека и популярные крейты отлично документированы, а `Ctrl+клик` в редакторе ведёт прямо в исходники.

**Темы, которые остались за рамками курса** — беритесь за них по мере надобности, не заранее:

| Тема | Когда понадобится |
|---|---|
| `unsafe` и FFI | связывание с C-библиотеками, низкий уровень |
| Макросы (`macro_rules!`, процедурные) | устранение повторов, свои `derive` |
| Асинхронность изнутри: `Pin`, `Poll` | своя реализация `Future` |
| Embedded, `no_std` | микроконтроллеры |
| WebAssembly | Rust в браузере |
| Оптимизация и профилирование | когда упрётесь в производительность |

## Что запомнить

- Проект закрепляет знания лучше, чем повторение теории.
- Начинайте с типов: в Rust хорошо спроектированные типы делают невозможные состояния непредставимыми.
- Прячьте хранилище за трейтом — так бизнес-логика тестируется без файлов и сети.
- Логика живёт в `lib.rs`, `main.rs` остаётся тонким.
- Джун — это не «знаю всё», а «читаю ошибки компилятора и довожу задачу до конца».
- Дальше учат не новые главы, а реальные задачи.

## Практика

**1. Ядро.** Реализуйте `Task`, `Status`, `TaskError` и `TaskList` с методами добавления, завершения, удаления и фильтрации. Готово, когда всё покрыто юнит-тестами и `cargo clippy` молчит.

**2. Хранилище.** Опишите трейт `Storage`, сделайте JSON-реализацию и тестовую в памяти. Готово, когда тесты бизнес-логики не трогают файловую систему.

**3. Интерфейс.** Добавьте CLI на `clap` с подкомандами `add`, `list`, `done`, `rm` и флагом пути к файлу. Готово, когда утилита работает end-to-end, а `--help` осмысленна.

**4. Полировка.** Добавьте поиск по подстроке, сортировку вывода, обработку всех ошибок с внятными сообщениями и doc-комментарии к публичному интерфейсу. Готово, когда в коде нет ни одного `unwrap` вне тестов.

**5. Расширение (по желанию).** Выберите одно: HTTP-API на `axum` поверх той же логики; хранение в SQLite через `sqlx`; асинхронная синхронизация с внешним сервисом. Готово, когда бизнес-логика не изменилась — только слой вокруг неё.
