# 2. Cargo: структура проекта, зависимости, clippy и rustfmt

В прошлой статье мы собрали программу вручную через `rustc`. Так почти никто не делает: как только файлов становится больше одного или появляется первая внешняя библиотека, ручная сборка превращается в мучение. Настоящий рабочий инструмент Rust — **Cargo**: он создаёт проекты, собирает их, качает зависимости, запускает тесты и форматирует код. Разберёмся с ним сразу, дальше все статьи будут опираться на него.

## Создание проекта

```bash
cargo new hello_cargo
cd hello_cargo
```

Получилась вот такая структура:

```
hello_cargo/
├── Cargo.toml
├── .gitignore
└── src/
    └── main.rs
```

Cargo сразу инициализировал git-репозиторий и положил в `.gitignore` строку `/target` — папку со сборкой в систему контроля версий не коммитят.

**`src/main.rs`** — точка входа, уже с готовым «Hello, world!». Весь исходный код живёт в папке `src/`.

**`Cargo.toml`** — манифест проекта:

```toml
[package]
name = "hello_cargo"
version = "0.1.0"
edition = "2024"

[dependencies]
```

Секция `[package]` описывает сам проект: имя, версию и **редакцию языка** (edition). Редакция выпускается раз в три года и фиксируется здесь навсегда: код, написанный для 2024, будет собираться и через десять лет, даже когда выйдут новые редакции. Секция `[dependencies]` пока пуста — сюда попадут внешние библиотеки.

## Сборка и запуск

Основная команда на каждый день — одна:

```bash
cargo run
```

```
   Compiling hello_cargo v0.1.0 (/path/to/hello_cargo)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.15s
     Running `target/debug/hello_cargo`
Hello, world!
```

Cargo собрал проект и сразу запустил результат. Запустите второй раз:

```
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.00s
     Running `target/debug/hello_cargo`
Hello, world!
```

Строчки `Compiling` нет — Cargo увидел, что исходники не менялись, и переиспользовал прошлую сборку. Всё это кэшируется в папке `target/`.

Полезно знать ещё три команды:

| Команда | Что делает | Когда нужна |
|---|---|---|
| `cargo check` | Проверяет код на ошибки, **не создавая бинарник** | Основной цикл разработки: в разы быстрее полной сборки |
| `cargo build` | Собирает бинарник в `target/debug/` | Когда нужен сам исполняемый файл |
| `cargo build --release` | Собирает с оптимизациями в `target/release/` | Только для готового продукта |

Разница между `debug` и `release` принципиальная. Отладочная сборка компилируется быстро, но программа работает медленно и содержит отладочную информацию. Релизная собирается заметно дольше, зато код оптимизирован — разница в скорости выполнения бывает десятикратной. Пока учитесь, сидите на `debug`: быстрая обратная связь важнее.

Отдельно обратите внимание на `cargo check`. В Rust компиляция небыстрая, и привычка проверять код именно так, а не полной сборкой, экономит массу времени.

## Зависимости

Библиотеки в Rust называются **крейтами** (crate) и живут на [crates.io](https://crates.io). Подключаются одной командой:

```bash
cargo add rand
```

```
      Adding rand v0.10.2 to dependencies
    Updating crates.io index
     Locking 8 packages to latest Rust compatible versions
```

В `Cargo.toml` появилась строка:

```toml
[dependencies]
rand = "0.10.2"
```

Теперь крейт можно использовать. Синтаксис разберём в следующих статьях, сейчас важен сам факт, что чужой код подключился:

```rust
use rand::RngExt;

fn main() {
    let number = rand::rng().random_range(1..=100);
    println!("Случайное число: {number}");
}
```

```
Случайное число: 34
```

Заметьте: вместе с `rand` подтянулись ещё 7 крейтов — это его собственные зависимости, Cargo разрешает всё дерево сам.

Рядом появился файл **`Cargo.lock`** с точными версиями и контрольными суммами всех крейтов. Разница между двумя файлами такая:

- `Cargo.toml` — что вы **хотите** («любая версия `rand`, совместимая с 0.10.2»). Пишете руками.
- `Cargo.lock` — что реально **установилось**. Генерируется автоматически, руками не редактируется, но **коммитится в репозиторий** — чтобы у коллеги и на сервере собралась ровно та же комбинация версий.

## Форматирование и линтер

Вместе с Rust идут два инструмента, которые стоит освоить сразу.

**`cargo fmt`** приводит код к единому официальному стилю. Возьмём неряшливый код:

```rust
fn main( ) {
let x=5;
      println!("{}",x);
}
```

После `cargo fmt`:

```rust
fn main() {
    let x = 5;
    println!("{}", x);
}
```

Никаких настроек и споров о стиле — в экосистеме Rust принято единообразие, и это экономит время на код-ревью.

**`cargo clippy`** — линтер. Он не ищет ошибки компиляции, он ищет **неидиоматичный код**: места, где вы написали работающе, но не по-растовски. Для новичка это бесплатный ментор. Пример:

```rust
if numbers.len() == 0 {
```

```
warning: length comparison to zero
 --> src/main.rs:5:8
  |
5 |     if numbers.len() == 0 {
  |        ^^^^^^^^^^^^^^^^^^ help: using `is_empty` is clearer and more explicit: `numbers.is_empty()`
  |
  = note: `#[warn(clippy::len_zero)]` on by default
```

Clippy знает больше 700 таких правил. Запускайте его регулярно и читайте объяснения — так вы быстрее всего наберёте идиоматику языка.

## Что запомнить

- `cargo new` создаёт проект: манифест `Cargo.toml`, исходники в `src/`, сборка в `target/`.
- `cargo run` — собрать и запустить, `cargo check` — быстро проверить без сборки бинарника.
- Отладочная сборка быстро компилируется, релизная (`--release`) быстро работает.
- Библиотеки называются крейтами, ставятся через `cargo add`, живут на crates.io.
- `Cargo.toml` пишете вы, `Cargo.lock` генерирует Cargo — и его коммитят в репозиторий, а `target/` нет.
- `cargo fmt` форматирует код по единому стилю, `cargo clippy` подсказывает, как писать идиоматично.

## Практика

**1. Первый проект.** Создайте проект `cargo_basics`, запустите его и найдите готовый бинарник в файловой системе. Запустите бинарник напрямую, без Cargo. Готово, когда программа отработала обоими способами.

**2. Скорость проверки.** Замерьте время `cargo check` и `cargo build` на чистом проекте (перед каждым замером удаляйте папку `target/`). Готово, когда у вас есть два числа и вы понимаете, почему они отличаются.

**3. Debug против release.** Соберите проект в обоих профилях и сравните размеры получившихся бинарников. Готово, когда можете объяснить разницу в размере.

**4. Зависимость.** Подключите крейт `rand` и напишите программу, которая выводит случайное число от 1 до 6 — имитацию броска кубика. Загляните в `Cargo.lock` и посчитайте, сколько крейтов там оказалось. Готово, когда программа при разных запусках выдаёт разные числа.

**5. Ментор в терминале.** Испортите форматирование своего кода (лишние пробелы, всё в одну строку) и почините через `cargo fmt`. Затем добавьте в программу строку, на которую ругнётся `cargo clippy`, прочитайте предупреждение и исправьте по подсказке. Готово, когда `cargo clippy` отрабатывает без единого warning.
