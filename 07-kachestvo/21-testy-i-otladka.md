# 21. Тесты, doc-тесты и отладка

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Компилятор Rust проверяет типы и работу с памятью, но не проверяет, что программа делает то, что задумано. За это отвечают тесты — и они встроены в язык: не нужен фреймворк, достаточно атрибута над функцией. Заодно разберём, как документация превращается в тесты и что делать, когда программа ведёт себя не так.

## Первый тест

Тест — это функция с атрибутом `#[test]`:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn складывает_положительные() {
        assert_eq!(add(2, 2), 4);
    }
}
```

Атрибут `#[cfg(test)]` над модулем означает «компилировать только при запуске тестов» — в готовый бинарник этот код не попадёт. `use super::*;` подтягивает всё из родительского модуля, чтобы тестировать в том числе приватные функции.

Имена тестов могут быть на русском — компилятор это допускает, и для учебного проекта читается отлично.

Запуск — `cargo test`:

```
running 6 tests
test tests::долгий_тест ... ignored
test tests::больше_нуля ... ok
test tests::складывает_положительные ... ok
test tests::это_упадёт ... FAILED
test tests::слишком_большое_значение - should panic ... ok
```

Тест считается провалившимся, если он паникует. Отсюда весь инструментарий:

- `assert!(условие)` — проверка на истинность;
- `assert_eq!(a, b)` и `assert_ne!(a, b)` — на равенство и неравенство;
- обычная `panic!` — если условие сложное.

К любому макросу можно добавить своё сообщение: `assert!(x > 0, "сумма должна быть положительной")`.

## Читаем провал

```
---- tests::это_упадёт stdout ----
thread 'tests::это_упадёт' panicked at src/lib.rs:47:9:
assertion `left == right` failed
  left: 4
 right: 5
```

`assert_eq!` печатает оба значения — сразу видно, что получилось и что ожидалось. Поэтому его предпочитают простому `assert!(a == b)`: тот сообщит только «условие ложно».

## Проверка паники

Иногда правильное поведение — упасть. Такое проверяют атрибутом:

```rust
#[test]
#[should_panic(expected = "должно быть от 1 до 100")]
fn слишком_большое_значение() {
    Guess::new(200);
}
```

Тест проходит, если функция паникнула, а сообщение содержит указанную подстроку. Параметр `expected` важен: без него тест засчитает **любую** панику, в том числе от постороннего бага.

Тест может возвращать `Result` — тогда `Err` означает провал, и внутри работает оператор `?`:

```rust
#[test]
fn с_result() -> Result<(), String> {
    if add(2, 2) == 4 { Ok(()) } else { Err(String::from("не сошлось")) }
}
```

## Управление запуском

Тесты по умолчанию идут **параллельно**, каждый в своём потоке. Отсюда правило: тесты не должны зависеть друг от друга и делить общее состояние — например, писать в один файл.

Полезные команды:

```bash
cargo test имя_теста        # запустить тесты, чьё имя содержит подстроку
cargo test -- --ignored     # запустить только помеченные #[ignore]
cargo test -- --test-threads=1   # последовательно
cargo test -- --show-output      # показать вывод println! из успешных тестов
```

Атрибут `#[ignore]` исключает тест из обычного прогона — для долгих проверок, которые запускают отдельно.

## Юнит-тесты и интеграционные

Разделение простое.

**Юнит-тесты** живут рядом с кодом, в модуле `#[cfg(test)]`. Видят приватные функции, проверяют детали реализации.

**Интеграционные** лежат в папке `tests/` в корне проекта. Каждый файл там — отдельный крейт, который подключает вашу библиотеку **снаружи**, как это сделал бы пользователь:

```rust
use a21::add;

#[test]
fn интеграционный() {
    assert_eq!(add(10, 10), 20);
}
```

Такой тест видит только публичный интерфейс. Если что-то не удаётся протестировать из `tests/` — это сигнал, что не хватает `pub`, или что интерфейс неудобен.

Важное ограничение: интеграционные тесты работают только с библиотечным крейтом. Поэтому в проектах логику обычно выносят в `src/lib.rs`, а `src/main.rs` оставляют тонкой оболочкой.

## Doc-тесты

Особенность Rust, которой стоит пользоваться. Документирующий комментарий начинается с `///`, поддерживает Markdown, а примеры кода в нём **выполняются как тесты**:

````rust
/// Складывает два числа.
///
/// # Примеры
///
/// ```
/// let sum = a21::add(2, 3);
/// assert_eq!(sum, 5);
/// ```
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}
````

```
   Doc-tests a21
running 1 test
test src/lib.rs - add (line 5) ... ok
```

Ценность в том, что примеры в документации **не могут устареть**: измените сигнатуру — и `cargo test` сразу покажет, что пример сломался. Именно поэтому документация в экосистеме Rust на удивление точна.

Команда `cargo doc --open` собирает из этих комментариев HTML-документацию.

## Отладка

Отладчик в Rust есть, но чаще обходятся тремя инструментами.

**`dbg!`** — печатает выражение вместе с файлом, строкой и результатом, а затем **возвращает значение**, поэтому вставляется прямо в середину выражения:

```rust
let b = dbg!(a * 2) + 1;
```

```
[dbg.rs:3:13] a * 2 = 10
```

В отличие от `println!`, ничего не нужно форматировать и потом вычищать — достаточно убрать обёртку.

**`{:?}` и `{:#?}`** — вывод структур через `Debug`, тот самый из статьи 17.

**`RUST_BACKTRACE=1`** — переменная окружения, показывающая цепочку вызовов при панике.

Для рабочих программ вместо печати используют логирование: крейты `log` (интерфейс) и `env_logger` (реализация) дают уровни важности и фильтрацию без правки кода.

## Что запомнить

- Тест — функция с `#[test]`; проваленным считается тест, который паникует.
- `assert_eq!` печатает оба значения, поэтому информативнее, чем `assert!`.
- `#[should_panic(expected = "...")]` проверяет ожидаемую панику; без `expected` тест слишком снисходителен.
- Тест может возвращать `Result`, и тогда внутри работает `?`.
- Тесты выполняются параллельно — они не должны делить состояние.
- Юнит-тесты в `#[cfg(test)]` видят приватное; интеграционные в `tests/` — только публичный интерфейс.
- Примеры в `///`-комментариях запускаются как тесты и потому не устаревают.
- `dbg!` печатает значение и возвращает его; `RUST_BACKTRACE=1` показывает стек при панике.

## Практика

**1. Первые тесты.** Напишите функцию, определяющую, является ли год високосным, и четыре теста: обычный год, високосный, столетие, столетие кратное 400. Готово, когда все четыре проходят.

**2. Читаем провал.** Намеренно сломайте функцию и запустите тесты. Разберите вывод: сколько провалилось, где, с какими значениями. Готово, когда можете найти проблемную строку, не глядя в код.

**3. Ожидаемая паника.** Напишите конструктор, паникующий на некорректных данных, и тест с `#[should_panic(expected = ...)]`. Затем измените текст паники, не трогая тест, и посмотрите на результат. Готово, когда понимаете ценность `expected`.

**4. Два уровня тестов.** Создайте библиотечный крейт с публичной и приватной функцией. Покройте обе юнит-тестами, затем добавьте интеграционный тест в `tests/`. Попробуйте вызвать из него приватную функцию. Готово, когда понимаете разницу в видимости.

**5. Doc-тест.** Задокументируйте публичную функцию с разделом «Примеры» и рабочим кодом. Убедитесь, что `cargo test` его запускает. Затем измените сигнатуру функции, не трогая документацию, и посмотрите, что произойдёт. Готово, когда doc-тест поймал расхождение.

2. Чем `assert_eq!` удобнее, чем `assert!(a == b)`?
3. Зачем в `#[should_panic]` указывать `expected` и чем плох тест без него?
4. Почему тесты не должны делить общее состояние?
5. В чём разница между юнит-тестами и интеграционными по расположению и видимости?
6. Почему логику проекта выносят в `lib.rs`, оставляя `main.rs` тонким?
7. Чем `dbg!` удобнее `println!` при отладке?
