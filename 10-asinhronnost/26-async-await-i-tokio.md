# 26. `async`/`await` и рантайм `tokio`

> ⏱ **~50 минут** · теория 20 мин · практика 30 мин

Потоки хороши, когда работа упирается в процессор. Но большинство серверных программ ничего не считает — они ждут: ответа базы, запроса по сети, чтения с диска. Держать поток ради ожидания расточительно: он занимает память и время планировщика, ничего не делая. Асинхронность решает именно эту задачу.

## Асинхронность против потоков

Разница в том, что происходит во время ожидания.

**Поток** блокируется: операционная система снимает его с процессора до готовности данных. Тысяча одновременных соединений — тысяча потоков, каждый со своим стеком в несколько мегабайт.

**Асинхронная задача** при ожидании **возвращает управление**. Рантайм тут же берёт другую задачу. Тысяча соединений обслуживается несколькими потоками, а задачи по памяти обходятся сотнями байт.

Правило выбора простое: **работа упирается в процессор — потоки, в ожидание — асинхронность**.

## `async` и `Future`

Функция с ключевым словом `async` возвращает не результат, а **будущее** (future) — описание работы, которую предстоит сделать:

```rust
async fn fetch(id: u32) -> String {
    sleep(Duration::from_millis(100)).await;
    format!("данные {id}")
}
```

Сигнатура говорит `-> String`, но на деле возвращается `impl Future<Output = String>`. Убедиться легко:

```rust
// ❌ не компилируется
let v = f();
println!("{v}");
```

```
error[E0277]: `impl Future<Output = u32>` doesn't implement `std::fmt::Display`
```

Достать результат из будущего можно только оператором `.await`. Он пишется после выражения — это удобно в цепочках: `client.get(url).await?.text().await?`.

Ключевое свойство: **будущее ленивое**, как итератор из статьи 20.

```rust
let lazy = fetch(99);
println!("будущее создано, но ничего не произошло");
println!("{}", lazy.await);
```

Пока нет `.await`, не выполняется ничего. Забытый `.await` — самая частая ошибка новичков, и компилятор о ней лишь предупреждает: код без него собирается, просто молча не работает.

## Рантайм

Стандартная библиотека Rust даёт синтаксис `async`/`await` и трейт `Future`, но **не даёт исполнителя**. Кто-то должен опрашивать задачи, следить за готовностью и распределять их по потокам. Этим занимается рантайм — внешний крейт.

Так сделано намеренно: серверу нужен многопоточный планировщик, микроконтроллеру — крошечный однопоточный. Язык не навязывает выбор.

Фактический стандарт — **tokio**:

```toml
[dependencies]
tokio = { version = "1", features = ["full"] }
```

```rust
#[tokio::main]
async fn main() {
    // ...
}
```

Атрибут `#[tokio::main]` разворачивается в обычную `main`, которая создаёт рантайм и запускает в нём ваш асинхронный код. Без рантайма `async fn main` просто не с чего исполнять.

## Последовательно или параллельно

Здесь новички теряют весь выигрыш. Посмотрите:

```rust
let a = fetch(1).await;
let b = fetch(2).await;
```

```
последовательно: данные 1, данные 2 за 204ms
```

Двести миллисекунд вместо ста. `.await` дожидается **первой** задачи, и только потом начинается вторая. Асинхронность сама по себе ничего не распараллеливает — она лишь позволяет не блокировать поток.

Чтобы задачи пошли одновременно, их нужно запустить вместе. Первый способ — `join!`:

```rust
let (a, b) = tokio::join!(fetch(3), fetch(4));
```

```
параллельно: данные 3, данные 4 за 101ms
```

Макрос ждёт все переданные будущие сразу и возвращает кортеж результатов.

Второй способ — `tokio::spawn`, когда задач много или их число заранее неизвестно:

```rust
let mut handles = vec![];
for i in 5..9 {
    handles.push(tokio::spawn(fetch(i)));
}
for h in handles {
    println!("{}", h.await.unwrap());
}
```

```
spawn за 102ms
```

Четыре задачи за время одной. `tokio::spawn` немедленно отдаёт задачу рантайму и возвращает дескриптор — по смыслу это аналог `thread::spawn`, только задачи легковесные. `unwrap` нужен, потому что задача могла паниковать.

Разница между ними: `join!` — фиксированный набор задач, известный при компиляции; `spawn` — динамический, и задачи могут исполняться на разных потоках.

## Чего нельзя делать в async

Одно правило важнее остальных: **не блокируйте асинхронный поток**.

```rust
std::thread::sleep(Duration::from_secs(1));      // ❌ в async-коде
tokio::time::sleep(Duration::from_secs(1)).await // ✓
```

Обычный `sleep` останавливает весь поток рантайма — вместе с сотнями чужих задач, которые на нём выполняются. То же касается блокирующего чтения файлов, тяжёлых вычислений и синхронных сетевых вызовов.

Если блокирующий код неизбежен (например, библиотека без асинхронного интерфейса), его выносят в отдельный пул: `tokio::task::spawn_blocking`.

## Что запомнить

- Асинхронность выгодна при ожидании ввода-вывода; для счётных задач нужны потоки.
- `async fn` возвращает `Future` — описание работы, а не результат.
- Результат достают через `.await`; будущее ленивое и без `.await` не выполняется.
- Рантайм не входит в стандартную библиотеку; фактический стандарт — `tokio`, подключается атрибутом `#[tokio::main]`.
- Два `.await` подряд выполняются **последовательно** — асинхронность сама по себе не распараллеливает.
- Для одновременного выполнения: `join!` для фиксированного набора, `tokio::spawn` для динамического.
- Блокирующие вызовы в async-коде останавливают весь поток рантайма; для них есть `spawn_blocking`.

## Практика

**1. Первая асинхронная программа.** Подключите tokio, напишите `async fn`, которая ждёт 500 мс и возвращает строку. Вызовите её из `#[tokio::main] async fn main`. Готово, когда программа печатает результат через полсекунды.

**2. Ленивость.** Создайте будущее, не вызывая `.await`, и напечатайте сообщение до и после. Убедитесь, что тело функции не выполнилось. Готово, когда видите, что ленивость реальна.

**3. Последовательно против параллельно.** Напишите три асинхронные функции по 300 мс каждая. Замерьте время при трёх `.await` подряд и через `join!`. Готово, когда есть два числа: около 900 мс и около 300 мс.

**4. Динамический набор задач.** Запустите десять задач через `tokio::spawn` с разным временем ожидания, соберите результаты. Готово, когда общее время близко к самой долгой задаче, а не к сумме.

**5. Блокировка рантайма.** Внутри асинхронной задачи вызовите `std::thread::sleep` и посмотрите, как это влияет на соседние задачи, запущенные через `spawn`. Затем замените на `tokio::time::sleep`. Готово, когда разница видна по времени выполнения.
