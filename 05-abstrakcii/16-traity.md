# 16. Трейты: `impl Trait`, trait bounds, `dyn Trait`

> ⏱ **~55 минут** · теория 25 мин · практика 30 мин

Трейт описывает поведение: набор методов, который тип обязуется предоставить. Если вы знакомы с интерфейсами из Java или Go — идея та же, но с важными отличиями. Это центральный механизм абстракции в Rust: на трейтах держатся операторы, циклы `for`, форматирование вывода и почти всё остальное.

## Объявление и реализация

```rust
trait Summary {
    fn author(&self) -> String;

    fn summarize(&self) -> String {
        format!("Читайте дальше... автор {}", self.author())
    }
}
```

Метод без тела — обязательный: его реализует каждый тип. Метод с телом — **реализация по умолчанию**, её можно взять как есть или переопределить.

```rust
struct Article { title: String, author: String }
struct Tweet { username: String }

impl Summary for Article {
    fn author(&self) -> String { self.author.clone() }
    fn summarize(&self) -> String { format!("{} — {}", self.title, self.author) }
}

impl Summary for Tweet {
    fn author(&self) -> String { format!("@{}", self.username) }
}
```

`Article` переопределил `summarize`, `Tweet` обошёлся умолчанием:

```
Rust растёт — Ерлан
Читайте дальше... автор @aliya
```

Реализация по умолчанию может звать обязательные методы — как здесь `summarize` зовёт `author`. Это позволяет описать много поведения через одну точку расширения: типу достаточно реализовать минимум.

Ключевое отличие от интерфейсов Java: **трейт реализуют отдельно от определения типа**. Структура объявлена в одном месте, реализация трейта — в другом, возможно, в другом модуле. Поэтому вы можете добавить своё поведение к чужим типам, включая типы из стандартной библиотеки.

## Правило сироты

Свобода не безгранична:

```rust
// ❌ не компилируется
impl std::fmt::Display for Vec<i32> { /* ... */ }
```

```
error[E0117]: only traits defined in the current crate can be implemented
              for types defined outside of the crate
  |
1 | impl std::fmt::Display for Vec<i32> {
  |                            `Vec` is not defined in the current crate
```

**Правило сироты**: в реализации `impl Trait for Type` хотя бы одно из двух — трейт или тип — должно принадлежать вашему крейту. Иначе две разные библиотеки могли бы реализовать один трейт для одного типа, и компилятор не знал бы, чью версию брать.

Обходной приём — обернуть чужой тип в свою кортежную структуру (как `Meters(f64)` из статьи 9) и реализовать трейт для обёртки.

## Трейт как параметр

Самое частое применение — принять «что угодно, умеющее это»:

```rust
fn notify(item: &impl Summary) {
    println!("Новость! {}", item.summarize());
}
```

Запись `&impl Summary` читается: «ссылка на любой тип, реализующий `Summary`». Функция работает и с `Article`, и с `Tweet`.

Это сокращение для полной формы с ограничением, знакомой по прошлой статье:

```rust
fn notify<T: Summary>(item: &T) { /* ... */ }
```

Когда ограничений много, их выносят в `where` — иначе сигнатура становится нечитаемой:

```rust
fn process<T, U>(a: &T, b: &U) -> String
where
    T: Summary + Clone,
    U: Summary + std::fmt::Debug,
{
    // ...
}
```

Трейт можно указать и в возвращаемом типе: `fn make() -> impl Summary` означает «вернётся какой-то конкретный тип, реализующий `Summary`, а какой — не ваше дело». Есть ограничение: все ветви функции должны возвращать **один и тот же** тип.

## Статическая и динамическая диспетчеризация

И вот тут возникает вопрос, который отличает Rust от языков с интерфейсами.

Всё, что мы писали выше, — **статическая диспетчеризация**. Работает мономорфизация из прошлой статьи: компилятор создаёт отдельную копию `notify` для каждого типа, вызовы прямые, всё можно встроить. Быстро и бесплатно.

Но иногда типы неизвестны при компиляции. Классический случай — список разнородных элементов:

```rust
// так нельзя: Vec требует единого типа
let list = vec![article, tweet];
```

Здесь нужна **динамическая диспетчеризация** — `dyn Trait`:

```rust
fn notify_all(items: &[Box<dyn Summary>]) {
    for item in items {
        println!("- {}", item.summarize());
    }
}

let list: Vec<Box<dyn Summary>> = vec![Box::new(a), Box::new(t)];
notify_all(&list);
```

`Box<dyn Summary>` — «указатель на что-то в куче, реализующее `Summary`». Конкретный тип забыт; при вызове метода программа смотрит в таблицу функций и находит нужную реализацию **во время выполнения**. `Box` разберём в статье 22, пока достаточно знать: он кладёт значение в кучу.

Это же решает и проблему с возвратом разных типов:

```rust
fn make_summary(flag: bool) -> Box<dyn Summary> {
    if flag {
        Box::new(Tweet { username: String::from("aliya") })
    } else {
        Box::new(Article { /* ... */ })
    }
}
```

| | `impl Trait` (статическая) | `dyn Trait` (динамическая) |
|---|---|---|
| Когда выбирается реализация | при компиляции | при выполнении |
| Стоимость вызова | нулевая, возможно встраивание | косвенный вызов через таблицу |
| Размер бинарника | копия на каждый тип | одна копия |
| Разнородная коллекция | невозможна | возможна |

**Практическое правило: по умолчанию `impl Trait`, а `dyn Trait` — когда типы обязаны различаться в рантайме.** Разница в скорости обычно несущественна, поэтому выбирайте по смыслу, а не из микрооптимизации.

## Что запомнить

- Трейт — набор методов, которые тип обязуется предоставить; методы с телом дают реализацию по умолчанию.
- Трейт реализуют отдельно от типа, в том числе для чужих типов.
- Правило сироты: либо трейт, либо тип должен быть вашим. Обход — обёртка в свою структуру.
- `&impl Trait` в параметре — сокращение для `<T: Trait>`; много ограничений выносят в `where`.
- `-> impl Trait` возвращает конкретный, но не названный тип; все ветви должны возвращать один и тот же.
- `dyn Trait` даёт динамическую диспетчеризацию: тип определяется в рантайме, зато возможны разнородные коллекции.
- По умолчанию — статика (`impl Trait`), динамика — когда без неё не обойтись.

## Практика

**1. Первый трейт.** Опишите трейт `Shape` с обязательным `area()` и реализацией по умолчанию `describe()`, использующей площадь. Реализуйте для `Circle` и `Square`. Готово, когда `describe` работает без переопределения в обоих типах.

**2. Переопределение.** Переопределите `describe` для одного из типов. Готово, когда два типа печатают разное, а код трейта не менялся.

**3. Правило сироты.** Попробуйте реализовать `Display` для `Vec<i32>` и разберите ошибку. Затем добейтесь цели через обёртку `struct Wrapper(Vec<i32>)`. Готово, когда обёртка печатается через `{}`.

**4. Два вида диспетчеризации.** Напишите функцию `print_area(s: &impl Shape)` и функцию `print_all(shapes: &[Box<dyn Shape>])`. Вызовите обе. Готово, когда во втором случае в одном векторе лежат разные фигуры.

**5. Возврат трейта.** Напишите функцию, возвращающую `Box<dyn Shape>` в зависимости от строкового параметра. Затем попробуйте переписать её на `-> impl Shape` и объясните, почему не выходит. Готово, когда можете сформулировать ограничение своими словами.
