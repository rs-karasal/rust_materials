# 17. Проектирование API и типов на Rust

> ⏱ **~40 минут** на проработку · грейды `[M]` `[S]`

Секция дизайна на Rust устроена иначе, чем на других языках: здесь меньше говорят про сервисы и очереди и больше — про типы. Причина в том, что в Rust проектирование типов **и есть** проектирование: правильные типы делают неверные состояния невозможными, и половина ошибок исчезает до написания логики.

---

## Главный принцип: невозможные состояния непредставимы

Это то, что интервьюер хочет услышать первым. Вместо структуры с флагами и необязательными полями описывают перечисление, где у каждого состояния ровно свои данные.

Плохо: структура заказа с полями «оплачен», «отменён», «дата оплаты», «причина отмены» — четыре поля дают шестнадцать комбинаций, из которых осмысленны три, и остальные придётся проверять руками в каждой функции.

Хорошо: перечисление `Order` с вариантами `Pending`, `Paid { at: DateTime }`, `Cancelled { reason: String }`. Невозможно получить отменённый заказ с датой оплаты — такого варианта просто нет. Плюс компилятор проверяет исчерпывающесть `match` и при добавлении варианта перечислит все места, требующие обработки.

**Что спросят следом.** «Где предел?» — когда вариантов становится десятки, читаемость падает; тогда разбивают на несколько типов. «Как быть с сериализацией?» — `serde` умеет перечисления с данными, формат настраивается атрибутами.

## Newtype: дешёвая типобезопасность

Обёртка над примитивом стоит одной строки и убирает целый класс ошибок:

```rust
struct UserId(u64);
struct OrderId(u64);
```

Теперь передать идентификатор заказа туда, где ждут пользователя, невозможно. В языке без этого приёма обе величины — `u64`, и ошибка обнаружится в проде.

Второе применение — валидация в конструкторе. Тип `Email`, создаваемый только через `Email::parse`, гарантирует корректность всем, кто его получил: проверять повторно не нужно нигде.

**Что спросят следом.** «Какова цена?» — в рантайме нулевая, `#[repr(transparent)]` гарантирует совпадение раскладки. «Что теряется?» — методы исходного типа; их пробрасывают вручную или через `Deref`, что спорно.

## Владение в сигнатурах: главный вопрос дизайна

Каждая сигнатура — это решение о владении, и его надо уметь обосновать.

- **`&T`** — функция только читает. Умолчание.
- **`&mut T`** — функция изменяет переданное значение.
- **`T`** — функция забирает владение: сохраняет значение, преобразует его или потребляет.

Практические правила: **параметры заимствованные, возврат владеющий**. То есть `&str` на входе и `String` на выходе, `&[T]` на входе и `Vec<T>` на выходе.

Отдельно про `impl Into<String>` в параметре: удобно для вызывающего, но усложняет сигнатуру и мономорфизацию. Берут, когда API публичный и удобство важно.

**Что спросят следом.** «Как понять, что API неудобен?» — если пользователю приходится клонировать перед каждым вызовом, значит, вы взяли владение там, где хватило бы ссылки. «Когда `Cow`?» — когда обычно возвращаете вход без изменений, но иногда меняете.

## Типизированное состояние

Приём для API, где порядок операций важен: состояние объекта выражают параметром типа, и методы существуют только у подходящего состояния.

```rust
struct Connection<S> { /* ... */ }
struct Disconnected;
struct Connected;

impl Connection<Disconnected> {
    fn connect(self) -> Connection<Connected> { /* ... */ }
}

impl Connection<Connected> {
    fn send(&self, data: &[u8]) { /* ... */ }
}
```

Вызвать `send` на неподключённом соединении невозможно — метода нет. Ошибка «not connected» исчезает из `Result` вовсе.

**Что спросят следом.** «Где это оправдано?» — в библиотеках с чётким жизненным циклом: соединения, транзакции, сборщики запросов. «А недостатки?» — типы усложняются, сообщения об ошибках становятся длиннее, динамическое хранение затрудняется.

## Ошибки: библиотека против приложения

Разделение, которое ждут:

**Библиотека** отдаёт конкретное перечисление ошибок (обычно через `thiserror`), потому что вызывающий код должен различать причины и реагировать по-разному. `Box<dyn Error>` в публичном API — плохое решение: пользователь не сможет ничего проверить.

**Приложение** использует `anyhow`: тип не важен, важна цепочка контекста для лога.

Дополнительно: помечайте публичные перечисления ошибок `#[non_exhaustive]`, чтобы добавление варианта не ломало пользователей.

**Что спросят следом.** «Что делать, если ошибок много?» — группировать по слоям: ошибка хранилища, ошибка домена, ошибка транспорта, с преобразованием на границах через `From`. «Когда паниковать?» — только при нарушении контракта API, и это должно быть в документации.

## Асинхронность в API: решение с последствиями

Вопрос, который стоит поднять самому: делать ли библиотеку асинхронной.

Асинхронный API привязывает пользователей к рантайму и заражает всё выше по стеку — это проблема цветных функций. Синхронный проще, но не годится для серверов.

Варианты: два интерфейса (как у `reqwest`), только синхронный с рекомендацией оборачивать в `spawn_blocking`, или только асинхронный с явным указанием рантайма. Для внутреннего кода компании обычно выбирают асинхронный и не мучаются.

**Что спросят следом.** «Как не привязываться к `tokio`?» — использовать только трейты из `futures`, но на практике это редко достижимо. «Что с трейтами?» — `async fn` в трейтах поддерживается, но для `dyn` всё ещё нужны обходы.

## Модули и границы

Раскладка типового сервиса на Rust:

```
src/
├── main.rs          // сборка зависимостей, запуск
├── lib.rs           // публичный интерфейс
├── domain/          // типы и бизнес-правила, без зависимостей
├── storage/         // реализация хранилища
└── api/             // HTTP-слой
```

Зависимости идут в одну сторону: `api` → `domain` ← `storage`. Домен объявляет **трейт** хранилища у себя, реализация живёт снаружи — тогда тесты домена обходятся заглушкой в памяти.

Модификатор `pub(crate)` позволяет открыть элемент внутри крейта, не выставляя наружу, — аналог `internal` в Go.

**Что спросят следом.** «Когда разбивать на несколько крейтов?» — когда время компиляции мешает или когда часть кода переиспользуется; workspace даёт общий `Cargo.lock`. «Как тестировать домен?» — заглушка, реализующая трейт, прямо в тестовом модуле.

## Что спрашивают про производительность

Ответ должен начинаться с «измерить», но в Rust добавляется специфика:

- **Аллокации** — главный источник; ищутся профилем кучи.
- **Клонирование** вместо заимствования — самый частый след неопытности.
- **`Box<dyn Trait>` в горячем пути** — косвенный вызов; иногда заменяется перечислением.
- **Мономорфизация** раздувает бинарник и время сборки; лечится выносом общей части в необобщённую функцию.

Важно уметь сказать, чего **не** надо делать: переписывать на `unsafe` без замера, менять структуры данных «на глаз», оптимизировать то, что не в горячем пути.

## Типичная задача секции

«Спроектируйте библиотеку для работы с очередью задач: постановка, получение, подтверждение обработки».

Что ожидается в ответе:

1. **Типы состояний.** Задача в очереди, задача в обработке, завершённая — перечисление или типизированное состояние.
2. **Владение.** Кто владеет задачей после получения; возвращается ли она в очередь при сбое.
3. **Ошибки.** Перечисление с вариантами «очередь пуста», «задача уже подтверждена», «хранилище недоступно».
4. **Асинхронность.** Нужна ли, и если да — как это повлияет на пользователей.
5. **Тестируемость.** Трейт хранилища, реализация в памяти.

Сильный ответ включает фразу: «подтверждение реализую так, чтобы забыть его было невозможно» — например, возвращать страж, который при уничтожении без явного подтверждения возвращает задачу в очередь. Это ровно тот способ мышления, который ценят в Rust.

## Красные флаги секции

- Структура с флагами вместо перечисления состояний.
- `String` как тип ошибки в публичном API.
- Владение в параметрах там, где хватило бы ссылки.
- `Box<dyn Error>` в библиотеке.
- Отсутствие ответа на вопрос «как это тестировать без внешних зависимостей».
- Нежелание обсуждать недостатки собственного дизайна.

## Что готовить заранее

Разберите три API и доведите до сигнатур: клиент внешнего сервиса, хранилище с транзакциями, парсер формата данных. Для каждого ответьте: какие типы состояний, где владение, какие ошибки, что делать асинхронным.
