# 12. Ловушки: трейты и времена жизни

> ⏱ **~30 минут** на проработку · 9 задач-ловушек · грейды `[M]` `[S]`

Вторая порция задач. Здесь ошибки тоньше: код часто компилируется, но ведёт себя не так, как ожидает автор, — либо не компилируется по причине, которую трудно связать с написанным.

---

### Ловушка 1: `impl Trait` и разные ветви `[M]`

```rust
fn make(flag: bool) -> impl Fn() -> i32 {
    if flag {
        || 1
    } else {
        || 2
    }
}
```

**Коротко.** Не компилируется: два замыкания имеют **разные анонимные типы**, а `impl Trait` означает «один конкретный тип, который я не называю».

**Подробно.** Ошибка выглядит как `if and else have incompatible types`, и она сбивает с толку: оба замыкания реализуют один трейт, но это не делает их одним типом. Каждое замыкание получает собственный тип, даже если сигнатуры совпадают.

Решение — `Box<dyn Fn() -> i32>`: динамическая диспетчеризация позволяет вернуть разные типы за одним интерфейсом, ценой выделения в куче и косвенного вызова.

**Что спросят следом.** «Почему `impl Trait` вообще существует, если есть `dyn`?» — статическая диспетчеризация без аллокации и с возможностью встраивания. «Где ещё это всплывает?» — при возврате разных итераторов из ветвей.

**Красные флаги.**
- Уверенность, что `impl Trait` работает как интерфейс из Java.

### Ловушка 2: `dyn Trait` без указателя `[M]`

```rust
let x: dyn Display = 5;
```

**Коротко.** Не компилируется: размер `dyn Trait` неизвестен на этапе компиляции, поэтому значение не может лежать на стеке напрямую. Нужен указатель: `&dyn Display`, `Box<dyn Display>`.

**Подробно.** Это следствие того, что `dyn Trait` — «неразмерный» тип (`!Sized`). Все обычные обобщения неявно требуют `Sized`, и именно поэтому для работы с `dyn` иногда пишут `T: ?Sized` — ослабление этого требования.

**Что спросят следом.** «Какие ещё типы неразмерные?» — срезы `[T]` и `str`, отсюда `&[T]` и `&str`. «Что такое толстый указатель?» — указатель на данные плюс метаданные: длина для среза, таблица функций для `dyn`.

**Красные флаги.**
- Незнание, что ссылка на `dyn` вдвое шире обычной.

### Ловушка 3: время жизни в структуре просачивается `[M]`

```rust
struct Parser<'a> {
    input: &'a str,
}

fn make_parser() -> Parser<'?> {
    let text = String::from("данные");
    Parser { input: &text }
}
```

**Коротко.** Написать такую функцию невозможно: `text` освобождается при выходе, и любое время жизни для результата будет неверным.

**Подробно.** Это фундаментальное ограничение структур со ссылками: они не могут пережить свои данные, поэтому их нельзя создать и вернуть из функции, которая эти данные породила. Параметр времени жизни просачивается во все типы, использующие структуру, — включая типы полей других структур.

Решение — либо владеющее поле (`String` вместо `&str`), либо передача данных снаружи: `fn make_parser(text: &str) -> Parser<'_>`.

**Что спросят следом.** «Что такое самоссылающаяся структура?» — та, где поле ссылается на другое поле того же значения; в безопасном Rust невозможна, для этого есть `Pin` и крейты вроде `ouroboros`. «Когда ссылки в структуре оправданы?» — в парсерах с нулевым копированием.

**Красные флаги.**
- Ссылки в полях структуры без ясной причины — источник каскада проблем.

### Ловушка 4: правило сироты и чужие типы `[M]`

```rust
impl Display for Vec<i32> { /* ... */ }
```

**Коротко.** Не компилируется: и трейт, и тип чужие. Правило сироты требует, чтобы хотя бы одно принадлежало вашему крейту.

**Подробно.** Зачем правило: иначе две библиотеки могли бы реализовать один трейт для одного типа по-разному, и добавление зависимости молча сломало бы поведение. Обход — newtype: обернуть `Vec<i32>` в свою структуру.

Ловушка в продолжении: newtype теряет все методы исходного типа. Возвращают их либо реализацией `Deref` (спорно, но распространено), либо ручным пробросом нужных.

**Что спросят следом.** «Можно ли реализовать свой трейт для `Vec<i32>`?» — да, трейт ваш. «А `From<Vec<i32>>` для своего типа?» — да, тип ваш.

**Красные флаги.**
- Незнание шаблона newtype при жалобе на невозможность реализовать трейт.

### Ловушка 5: `Default` и частичная инициализация `[J/M]`

```rust
#[derive(Default)]
struct Config {
    host: String,
    port: u16,
    debug: bool,
}

let c = Config { port: 8080, ..Default::default() };
```

**Коротко.** Компилируется и работает: `port` равен 8080, остальные поля — значения по умолчанию.

**Подробно.** Ловушка в том, что `port: u16` со значением по умолчанию — это **ноль**, и отличить «не задано» от «задано нулём» невозможно. Для конфигураций это приводит к тихим ошибкам: пользователь не указал порт, приложение слушает нулевой.

Решение — `Option<u16>` с явной проверкой либо ручная реализация `Default` с осмысленными значениями вместо нулевых.

**Что спросят следом.** «Когда `derive(Default)` уместен?» — когда нулевые значения действительно осмысленны. «Что даёт синтаксис `..Default::default()`?» — заполнение остальных полей; работает с любым значением, не только с умолчанием.

**Красные флаги.**
- `derive(Default)` на конфигурации без проверки, что нули имеют смысл.

### Ловушка 6: `PartialEq` без `Eq` `[M]`

```rust
#[derive(PartialEq, Eq, Hash)]
struct Point { x: f64, y: f64 }
```

**Коротко.** Не компилируется: `f64` не реализует `Eq`, потому что `NaN != NaN`. Следовательно, структура с полем `f64` не может быть ни `Eq`, ни `Ord`, ни ключом `HashMap`.

**Подробно.** Это регулярно ломает планы: координаты, суммы денег, коэффициенты — всё это дробные числа, и все они не могут быть ключами карты. Решения: хранить целое в минимальных единицах (тиыны вместо тенге), использовать обёртку с проверкой на `NaN` (`ordered-float`), либо округлять и хранить целое.

**Что спросят следом.** «Почему `NaN != NaN`?» — требование стандарта IEEE 754, где `NaN` означает «не число» и не равен ничему, включая себя. «Как отсортировать `Vec<f64>`?» — `sort_by(|a, b| a.partial_cmp(b).unwrap())` с риском паники на `NaN`, либо `total_cmp`.

**Красные флаги.**
- Попытка использовать деньги как `f64` — отдельная проблема, о которой стоит сказать.

### Ловушка 7: `Iterator` и повторный проход `[M]`

```rust
let v = vec![1, 2, 3];
let it = v.iter();
let sum: i32 = it.sum();
let count = it.count();
```

**Коротко.** Не компилируется: `sum()` **поглощает** итератор, и `it` больше недоступен. Большинство потребителей забирают `self` по значению.

**Подробно.** Это отличается от языков, где итератор — объект, который можно опросить дважды. Здесь итератор одноразовый, и это делает ленивость безопасной: невозможно случайно пройти по данным дважды, думая, что они не изменились.

Решение — создать итератор заново или собрать в коллекцию: `let items: Vec<_> = v.iter().collect();`.

**Что спросят следом.** «Что такое `by_ref`?» — заимствование итератора, позволяющее взять часть элементов и продолжить с остальными. «Что такое `peekable`?» — обёртка, позволяющая заглянуть в следующий элемент, не потребляя его.

**Красные флаги.**
- Незнание `by_ref` при работе с частичным потреблением.

### Ловушка 8: обобщение и `dyn` в одном контейнере `[M/S]`

```rust
let shapes = vec![Circle(1.0), Square(2.0)];
```

**Коротко.** Не компилируется: `Vec<T>` требует единого типа, а `Circle` и `Square` — разные. Нужен `Vec<Box<dyn Shape>>` либо перечисление.

**Подробно.** Ловушка в том, что кандидаты обычно называют только `dyn`, забывая про перечисление. Перечисление часто лучше: нет косвенного вызова, нет аллокации, компилятор проверяет исчерпывающесть `match`. Цена — закрытый набор вариантов и невозможность расширить снаружи.

**Что спросят следом.** «Когда точно нужен `dyn`?» — когда типы добавляют пользователи вашей библиотеки. «Что такое `enum_dispatch`?» — приём, превращающий перечисление в замену трейт-объекту ради скорости.

**Красные флаги.**
- `Box<dyn Trait>` как единственный рассматриваемый вариант.

### Ловушка 9: `'static` в ограничении обобщения `[S]`

```rust
fn spawn_task<T: 'static>(value: T) { /* ... */ }
```

**Коротко.** `T: 'static` **не** означает «значение живёт всю программу». Оно означает «тип не содержит нестатических ссылок», то есть значение **может** жить сколько угодно. `String` этому удовлетворяет, `&'a str` — нет.

**Подробно.** Смешение двух смыслов `'static` — одна из самых частых путаниц. Первый смысл — время жизни ссылки (`&'static str`), второй — ограничение типа. Именно второй требуется в `thread::spawn` и `tokio::spawn`: задача может пережить создавшую её функцию, поэтому не должна держать временных ссылок.

**Что спросят следом.** «Почему тогда `String` проходит?» — он владеет данными и не заимствует ничего временного. «Как передать заимствованные данные в поток?» — `thread::scope`, гарантирующий завершение до конца области видимости.

**Красные флаги.**
- «`'static` значит навсегда» — верно только для первого смысла.

## Как этим пользоваться

**Менти.** Ловушки этого раздела сводятся к трём вопросам: сколько здесь конкретных типов на самом деле; известен ли размер типа на этапе компиляции; что именно это ограничение требует от типа. Разберите каждую до объяснения вслух.

**Ментор.** Ловушки 1 и 8 показывают, понимает ли кандидат разницу между статической и динамической диспетчеризацией на практике. Ловушка 9 — надёжный маркер уровня: путаница в двух смыслах `'static` встречается даже у людей с годом опыта.
