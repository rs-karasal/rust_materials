# 11. Ловушки: владение и заимствование

> ⏱ **~30 минут** на проработку · 10 задач-ловушек · грейды `[J]` `[M]` `[S]`

В Rust ловушки устроены иначе, чем в Go: большинство неверных вариантов просто **не компилируется**, поэтому вопрос обычно звучит «скомпилируется ли и почему». Это делает задачи ценнее — они проверяют модель в голове, а не память на поведение.

Все выводы получены запуском, все ошибки — настоящие сообщения компилятора.

---

### Ловушка 1: `for` по вектору без ссылки `[J]`

```rust
let v = vec![1, 2, 3];
for x in v {
    println!("{x}");
}
println!("{v:?}");   // ?
```

**Коротко.** Не компилируется: `borrow of moved value: v`. Цикл `for x in v` вызывает `into_iter()` и **поглощает** вектор.

**Подробно.** Чтобы вектор остался жив, пишут `for x in &v` — это вызывает `iter()` и даёт ссылки. Проверено: `v.iter().sum()` оставляет вектор доступным, `v.into_iter().sum()` — нет.

Это самая частая потеря владения у новичков, и она же объясняет, почему в чужом коде так часто видно `&` перед коллекцией в цикле.

**Что спросят следом.** «А если нужно изменить элементы?» — `for x in &mut v` и `*x` для доступа. «Когда `into_iter` предпочтительнее?» — когда элементы нужны по значению и коллекция больше не нужна: избегаете клонирования.

**Красные флаги.**
- Клонирование вектора перед циклом, чтобы «сохранить оригинал».

### Ловушка 2: ссылка на элемент и `push` `[M]`

```rust
let mut v = vec![1, 2, 3];
let first = &v[0];
v.push(4);
println!("{first}");
```

**Коротко.** Не компилируется — `E0502`. Пока жива неизменяемая ссылка на элемент, вектор нельзя изменять.

**Подробно.** Причина конкретна: `push` может перевыделить буфер, скопировать данные и освободить старый, — тогда `first` указывал бы в освобождённую память. В C++ это классический баг с невалидированным итератором, проявляющийся случайно в зависимости от ёмкости.

Проверьте себя: если убрать `println!`, код **скомпилируется** — благодаря NLL заимствование заканчивается на последнем использовании ссылки.

**Что спросят следом.** «Как обойти?» — скопировать значение (`let first = v[0];`), работать по индексу или закончить с ссылкой до изменения. «Почему нельзя разрешить, если ёмкости хватает?» — компилятор не знает ёмкость на этапе компиляции.

**Красные флаги.**
- «Компилятор перестраховывается» — здесь есть конкретный сценарий порчи памяти.

### Ловушка 3: что останется после `mem::take` `[M]`

```rust
let mut owner = vec![String::from("a")];
let taken = std::mem::take(&mut owner[0]);
println!("{taken:?} {owner:?}");
```

**Коротко.** Печатает `"a" [""]`. `mem::take` забирает значение и подставляет на его место **значение по умолчанию** — для `String` это пустая строка.

**Подробно.** Приём нужен потому, что переместить значение из-под ссылки (например, из элемента вектора или поля структуры за `&mut`) напрямую нельзя: это оставило бы «дырку», а Rust требует, чтобы значение всегда было валидным.

Родственный `mem::replace` подставляет заданное значение вместо умолчания, `mem::swap` меняет два значения местами.

**Что спросят следом.** «Зачем это нужно на практике?» — забрать содержимое поля в методе с `&mut self`, не клонируя его. «Что требуется от типа?» — `Default` для `take`, ничего для `replace`.

**Красные флаги.**
- Клонирование там, где достаточно `mem::take`.

### Ловушка 4: `match` поглощает значение `[M]`

```rust
let opt = Some(String::from("v"));
match opt {
    Some(s) => println!("{s}"),
    None => {}
}
println!("{opt:?}");   // ?
```

**Коротко.** Не компилируется: `match opt` переместил `String` в переменную `s`, и `opt` больше недоступен. Достаточно написать `match &opt` — проверено, тогда всё работает.

**Подробно.** Правило: сопоставление с образцом следует общим правилам владения. Если тип не `Copy`, разбор по значению его поглощает. Варианты решения: `match &opt`, `opt.as_ref()`, либо образец `Some(ref s)` в старом стиле.

С Go это сравнивать нечем: там `switch` ничего не поглощает, потому что владения нет вовсе.

**Что спросят следом.** «А если нужно и разобрать, и сохранить?» — `if let Some(s) = &opt`. «Что такое match ergonomics?» — правила, позволяющие писать `Some(s)` при сопоставлении со ссылкой и получать `s` как ссылку автоматически.

**Красные флаги.**
- Клонирование перед `match` вместо взятия ссылки.

### Ловушка 5: изменение вектора во время обхода `[M]`

```rust
let mut v = vec![1, 2, 3];
for x in &v {
    if *x == 2 {
        v.push(4);
    }
}
```

**Коротко.** Не компилируется: `cannot borrow v as mutable because it is also borrowed as immutable`. Цикл держит неизменяемое заимствование всё время обхода.

**Подробно.** В Go такой код собрался бы, а в Python — вызвал бы неопределённое поведение при обходе списка. Здесь это ошибка компиляции, и это ровно тот случай, ради которого правило заимствования существует.

Решение: собрать нужные изменения в отдельный вектор и применить после цикла, либо обходить по индексу с проверкой длины на каждой итерации.

**Что спросят следом.** «Как удалить элементы по условию?» — `v.retain(|x| ...)`, один проход без выделения. «А если нужно и добавлять, и удалять?» — построить новый вектор.

**Красные флаги.**
- Попытка обойти через `RefCell` вместо изменения алгоритма.

### Ловушка 6: два изменяемых заимствования полей `[M/S]`

```rust
struct P { a: i32, b: i32 }

let mut p = P { a: 1, b: 2 };
let ra = &mut p.a;
let rb = &mut p.b;
*ra += *rb;
```

**Коротко.** Компилируется. Компилятор отслеживает заимствования **по отдельным полям**, а не по структуре целиком, поэтому две изменяемые ссылки на разные поля допустимы.

**Подробно.** Ловушка в продолжении: если попытаться сделать то же через методы (`p.get_a_mut()` и `p.get_b_mut()`), код не соберётся — метод заимствует `self` целиком, и компилятор теряет информацию о полях.

Это одно из самых частых мест, где borrow checker кажется нелогичным: прямой доступ работает, а через геттеры нет. Решение — метод, возвращающий обе ссылки сразу, или разделение структуры.

**Что спросят следом.** «А для элементов вектора?» — `v[0]` и `v[1]` одновременно изменяемо взять нельзя: индексы вычисляются в рантайме. «Что тогда?» — `split_at_mut`, разделяющий срез на две непересекающиеся части.

**Красные флаги.**
- Незнание `split_at_mut` при работе с срезами.

### Ловушка 7: замыкание захватывает по-разному `[M]`

```rust
let mut count = 0;
let mut inc = || count += 1;
inc();
inc();
println!("{count}");   // ?
```

**Коротко.** Печатает `2`. Замыкание захватило `count` по изменяемой ссылке, поэтому само объявлено с `mut`. После последнего вызова заимствование заканчивается, и `count` снова доступен.

**Подробно.** Ловушка в том, что если поставить `println!("{count}")` **между** вызовами, код не скомпилируется: изменяемое заимствование ещё живо. Компилятор выбирает наименее ограничивающий способ захвата — по неизменяемой ссылке, по изменяемой или по значению.

Проверено также move-замыкание: `move || text.len()` забирает владение, и исходная переменная становится недоступной.

**Что спросят следом.** «Когда нужен `move`?» — когда замыкание переживает текущую область: уходит в поток, в `tokio::spawn` или возвращается из функции. «Что означают `Fn`, `FnMut`, `FnOnce`?» — только читает, изменяет, поглощает.

**Красные флаги.**
- `move` везде «на всякий случай» — иногда это лишнее клонирование.

### Ловушка 8: возврат ссылки на локальное значение `[J]`

```rust
fn make() -> &String {
    let s = String::from("x");
    &s
}
```

**Коротко.** Не компилируется: `missing lifetime specifier`, а при попытке добавить `'a` — `does not live long enough`. Локальное значение освобождается при выходе, ссылка стала бы висячей.

**Подробно.** Компилятор подсказывает `'static`, и эту подсказку **не надо принимать**: она лечит симптом. Правильное решение — вернуть владение: `fn make() -> String`.

Отдельно стоит понимать, что возврат владения дёшев: перемещение копирует только шапку, а не содержимое кучи.

**Что спросят следом.** «Как всё же вернуть ссылку?» — только на данные из аргументов или на `'static`. «Чем это отличается от Go?» — там escape-анализ перенёс бы значение в кучу, и код был бы корректен.

**Красные флаги.**
- Принятие подсказки про `'static` без размышлений.

### Ловушка 9: `String` против `&str` в сравнении `[J/M]`

```rust
let owned = String::from("привет");
let literal = "привет";
println!("{}", owned == literal);
```

**Коротко.** Компилируется и печатает `true`. Стандартная библиотека реализует сравнение между `String` и `&str` специально.

**Подробно.** Ловушка в обратном: `Vec<String>` и `Vec<&str>` сравнить нельзя — такой реализации нет. И `owned == literal.to_string()` тоже работает, но выделяет память зря.

Продолжение злее: `"а" < "б"` сравнивает по байтам UTF-8, а не по алфавиту локали, поэтому сортировка строк с кириллицей не совпадает с ожиданиями пользователя. Для человеческой сортировки нужен внешний крейт.

**Что спросят следом.** «Как сравнить без учёта регистра?» — `eq_ignore_ascii_case` для латиницы, для юникода — `to_lowercase()` обеих сторон или специальный крейт. «Почему `to_lowercase` возвращает `String`?» — в юникоде длина может измениться.

**Красные флаги.**
- Уверенность, что лексикографическое сравнение строк совпадает с алфавитным порядком языка.

### Ловушка 10: `Copy` для структуры с ссылкой `[S]`

```rust
#[derive(Clone, Copy)]
struct Wrapper<'a> {
    data: &'a str,
}
```

**Коротко.** Компилируется. Неизменяемая ссылка `&T` реализует `Copy`, поэтому структура с ней тоже может быть `Copy`.

**Подробно.** Ловушка в контрасте: `&mut T` **не** `Copy` — иначе можно было бы получить две изменяемые ссылки простым присваиванием, что нарушило бы главное правило языка. Именно поэтому изменяемые ссылки «перезаимствуются» (reborrow) при передаче в функцию, а не копируются.

**Что спросят следом.** «Почему `&mut T` не `Copy`, а `&T` — да?» — копирование неизменяемой ссылки безопасно, копирование изменяемой создало бы алиас. «Что такое reborrow?» — неявное создание новой изменяемой ссылки на время вызова; поэтому `&mut` можно передавать в функцию несколько раз подряд.

**Красные флаги.**
- Незнание, что `&mut T` не `Copy`, при попытке объяснить, почему код с двумя вызовами компилируется.

## Как этим пользоваться

**Менти.** В Rust полезнее всего натренировать три вопроса: это поглощение или заимствование; что здесь `Copy`, а что нет; где заканчивается последнее использование ссылки. Почти все ловушки раздела сводятся к одному из них.

**Ментор.** Ловушки 2 и 5 показывают, понимает ли кандидат **зачем** нужно правило заимствования, а не только как его обойти. Ловушка 6 — хороший тест на middle: она объясняет, почему borrow checker иногда кажется нелогичным, и знание про `split_at_mut` сразу выдаёт практику.
