# 13. Ловушки: конкурентность и async

> ⏱ **~30 минут** на проработку · 9 задач-ловушек · грейды `[M]` `[S]`

Последняя порция. Здесь ловушки самые практичные: часть кода не компилируется по причинам, которые сначала кажутся загадочными, а часть компилируется и ведёт себя неожиданно — зависает или теряет работу.

---

### Ловушка 1: `Rc` в потоке `[M]`

```rust
let data = Rc::new(5);
let d = Rc::clone(&data);
thread::spawn(move || println!("{d}"));
```

**Коротко.** Не компилируется: `Rc<i32> cannot be sent between threads safely` — он не реализует `Send`.

**Подробно.** Причина конкретна: счётчик ссылок обновляется неатомарно, поэтому два потока могут потерять увеличение, счётчик обнулится раньше времени и произойдёт освобождение живых данных. Замена — `Arc`, интерфейс идентичен.

Ловушка в том, что сообщение указывает на замыкание, а не на `Rc`, и новичок ищет проблему не там. Читать надо строку `the trait Send is not implemented for Rc<i32>`.

**Что спросят следом.** «Почему тогда не использовать `Arc` всегда?» — атомарные операции дороже. «Что если внутри `Arc` лежит `RefCell`?» — не скомпилируется: `RefCell` не `Sync`, нужен `Mutex`.

**Красные флаги.**
- Попытка обойти через `unsafe impl Send`.

### Ловушка 2: страж мьютекса через `.await` `[M/S]`

```rust
let guard = mutex.lock().unwrap();
some_async_fn().await;
drop(guard);
```

**Коротко.** Не компилируется при отправке в `tokio::spawn`: `future cannot be sent between threads safely`, потому что страж обычного `std::sync::Mutex` не `Send` и живёт через точку ожидания.

**Подробно.** Компилятор указывает на переменную, удерживаемую через `.await`, — и это подсказка, а не шум. Два решения: освободить страж **до** `.await` (часто достаточно обернуть работу в блок `{}`), либо использовать асинхронный `tokio::sync::Mutex`.

Важно не перепутать: асинхронный мьютекс нужен, **только** если под замком есть точка ожидания. Для коротких секций обычный быстрее.

**Что спросят следом.** «Почему сообщение указывает на странную строку?» — она показывает, что именно живёт через `.await`. «А если нужен `Rc` в асинхронной задаче?» — либо `Arc`, либо однопоточный рантайм и `spawn_local`.

**Красные флаги.**
- Замена всех мьютексов на асинхронные «для единообразия».

### Ловушка 3: `.await` в цикле `[M]`

```rust
let mut results = Vec::new();
for url in urls {
    results.push(fetch(url).await);
}
```

**Коротко.** Компилируется и работает, но выполняется **строго последовательно**: время равно сумме, а не максимуму. Асинхронность сама по себе не распараллеливает.

**Подробно.** Это самая частая потеря производительности в асинхронном коде, и компилятор о ней молчит. Решение — собрать будущие и запустить вместе: `futures::future::join_all`, `tokio::spawn` с последующим ожиданием дескрипторов, либо `FuturesUnordered` для потоковой обработки.

Замерено в курсе: две операции по 100 мс дали 204 мс последовательно и 101 мс через `join!`.

**Что спросят следом.** «Как ограничить параллелизм?» — `buffer_unordered(n)` у потока будущих либо семафор. «Почему не запускать всё сразу?» — тысяча одновременных запросов положит и вас, и зависимость.

**Красные флаги.**
- Уверенность, что `async` делает код параллельным.

### Ловушка 4: забытый `.await` `[J/M]`

```rust
async fn save(data: &str) { /* ... */ }

save("важные данные");   // без .await
```

**Коротко.** Код компилируется, но **ничего не делает**: будущее создано и тут же уронено. Компилятор выдаёт предупреждение `unused implementer of Future`, а не ошибку.

**Подробно.** Ловушка опаснее, чем кажется, потому что ленивость будущих неочевидна тем, кто пришёл из JavaScript, где промис начинает выполняться сразу при создании. Симптом в проде: операция «иногда не срабатывает», хотя ошибок нет.

Защита — включить `#![deny(unused_must_use)]` в крейте, тогда предупреждение станет ошибкой.

**Что спросят следом.** «Чем это отличается от промиса?» — промис уже запущен, будущее — только описание. «Что делает `tokio::spawn` без ожидания дескриптора?» — задача выполнится, но результат и паника будут потеряны.

**Красные флаги.**
- Предупреждения компилятора игнорируются.

### Ловушка 5: отмена в `select!` теряет работу `[S]`

```rust
tokio::select! {
    _ = write_to_file(data) => {}
    _ = tokio::time::sleep(timeout) => {}
}
```

**Коротко.** Если сработает таймаут, запись в файл будет **отменена посередине** — на последней точке `.await`. Файл останется частично записанным, и никакого уведомления задача не получит.

**Подробно.** Отмена в Rust мгновенна: будущее просто перестают опрашивать и роняют. Это отличается от Go, где контекст — кооперативный сигнал, и функция сама решает, когда выйти.

Отсюда понятие безопасности к отмене. Неразрывные операции выносят в `tokio::spawn`: отдельная задача переживёт отмену `select!`, и её можно дождаться отдельно.

**Что спросят следом.** «Какие операции безопасны к отмене?» — те, что при прерывании не оставляют системы в противоречивом состоянии; в документации `tokio` это указано явно. «Классический пример небезопасной?» — `recv` из канала, где сообщение уже извлечено, но не обработано.

**Красные флаги.**
- Использование `select!` без понимания, что происходит с проигравшими ветвями.

### Ловушка 6: блокирующий вызов в асинхронной задаче `[M]`

```rust
async fn handler() {
    std::thread::sleep(Duration::from_secs(1));
}
```

**Коротко.** Компилируется без единого предупреждения, но останавливает **весь поток рантайма** вместе с сотнями чужих задач на нём.

**Подробно.** Правильный вариант — `tokio::time::sleep(...).await`. То же касается синхронного чтения файлов, тяжёлых вычислений и блокирующих вызовов из библиотек без асинхронного интерфейса: их выносят в `tokio::task::spawn_blocking`.

Симптом в проде: растёт задержка при низкой нагрузке, часть запросов «зависает» без видимой причины. Находится через `tokio-console` по времени опроса задачи.

**Что спросят следом.** «Как понять, что вызов блокирующий?» — по типу: если функция не `async` и делает ввод-вывод, она блокирует. «Сколько можно блокировать?» — ориентир десятки микросекунд; дольше — в отдельный пул.

**Красные флаги.**
- `std::thread::sleep` в асинхронном коде.

### Ловушка 7: взаимоблокировка на двух мьютексах `[M]`

```rust
// поток 1
let a = m1.lock().unwrap();
let b = m2.lock().unwrap();

// поток 2
let b = m2.lock().unwrap();
let a = m1.lock().unwrap();
```

**Коротко.** Компилируется. Зависает намертво, если потоки войдут одновременно. Rust **не предотвращает** взаимоблокировки — он гарантирует только отсутствие гонок данных.

**Подробно.** Это важный вопрос для проверки: кандидат, считающий, что «Rust безопасен для многопоточности», должен уметь назвать, что именно язык не гарантирует. Кроме взаимоблокировок это состояния гонки на уровне логики, утечки памяти и голодание.

Правила профилактики те же, что везде: захватывать мьютексы в едином порядке, держать замок как можно короче, не вызывать под замком чужой код.

**Что спросят следом.** «Как отлаживать?» — стеки всех потоков, `parking_lot` с обнаружением взаимоблокировок, тесты с таймаутом. «Что такое `loom`?» — библиотека, перебирающая расписания потоков для конкурентных структур.

**Красные флаги.**
- «В Rust взаимоблокировок не бывает».

### Ловушка 8: паника под замком отравляет мьютекс `[M/S]`

```rust
let guard = m.lock().unwrap();
risky_operation();   // паникует
```

**Коротко.** Мьютекс становится **отравленным**: все последующие `lock()` возвращают `Err`. Это специфика Rust, которой нет в Go, где замок просто остаётся захваченным.

**Подробно.** Логика такая: паника под замком могла оставить данные в противоречивом состоянии, поэтому остальные потоки должны об этом узнать. Обычно пишут `.unwrap()` и падают дальше; если состояние восстановимо, ошибка даёт доступ к данным через `into_inner()`.

Ловушка в контрасте с Go: там аналогичная ситуация даёт вечное зависание на `Lock`, здесь — явную ошибку. Отравление — это фича, а не проблема.

**Что спросят следом.** «Почему `parking_lot::Mutex` не отравляется?» — авторы сочли, что цена проверки выше пользы; там `lock()` не возвращает `Result`. «Что выбрать?» — стандартный по умолчанию, `parking_lot` при доказанной необходимости.

**Красные флаги.**
- Незнание, что `lock()` возвращает `Result`, и почему.

### Ловушка 9: задача, которую никто не ждёт `[M]`

```rust
tokio::spawn(async {
    do_work().await;
});
// дескриптор отброшен
```

**Коротко.** Задача выполнится, но её результат и паника будут потеряны молча. Кроме того, при завершении рантайма незавершённые задачи просто обрываются.

**Подробно.** Это асинхронный аналог утечки горутин: задачи копятся, никто не знает об их отказах. Для фоновых задач принято сохранять дескрипторы и дожидаться их при завершении, либо использовать `JoinSet`, который позволяет ждать группу и получать ошибки.

Отдельно: `tokio::spawn` без ожидания не гарантирует, что задача вообще успеет начаться, если рантайм завершится сразу.

**Что спросят следом.** «Как корректно останавливать фоновые задачи?» — токен отмены (`CancellationToken`) плюс ожидание завершения. «Что такое `JoinSet`?» — коллекция задач с возможностью получать результаты по мере готовности.

**Красные флаги.**
- `tokio::spawn` для важной работы без сохранения дескриптора.

## Как этим пользоваться

**Менти.** Задавайте себе четыре вопроса на любой конкурентный фрагмент: что здесь живёт через `.await`; что происходит при отмене; есть ли блокирующий вызов; кто дождётся этой задачи. Почти все ловушки раздела отвечают на один из них.

**Ментор.** Ловушки 3 и 6 не дают ни ошибки, ни предупреждения — только неверное поведение, поэтому они лучше всего отделяют тех, кто писал асинхронный код в проде. Ловушка 7 обязательна для senior: ответ на неё показывает, читал ли человек про язык что-то кроме рекламных формулировок.
