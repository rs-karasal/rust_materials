# 15. Задачи уровня middle

> ⏱ **~75 минут** на проработку · 5 задач по 15–20 минут · грейд `[M]`

На middle задачи проверяют проектирование типов: как человек описывает предметную область перечислениями, где ставит границы ошибок и умеет ли выбирать между владением и заимствованием осознанно.

Все решения проверены запуском.

---

### Задача 1: лексический разбор с собственным типом ошибки `[M]` · ~20 мин

**Условие.** Разберите строку вида `"1 + 2"` в последовательность токенов. Ошибки должны быть информативными: что именно не разобралось.

**На что смотрит интервьюер.**

- Описывает ли токены **перечислением**, а не строками с флагами.
- Заводит ли собственный тип ошибки вместо `String`.
- Реализует ли `Display` и `std::error::Error`.
- Обрабатывает ли пустой ввод отдельным вариантом.

**Решение.**

```rust
#[derive(Debug, PartialEq)]
enum Token {
    Num(f64),
    Op(char),
}

#[derive(Debug)]
enum ParseErr {
    BadChar(char),
    Empty,
}

impl fmt::Display for ParseErr {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ParseErr::BadChar(c) => write!(f, "недопустимый символ {c:?}"),
            ParseErr::Empty => write!(f, "пустой ввод"),
        }
    }
}
impl std::error::Error for ParseErr {}

fn tokenize(s: &str) -> Result<Vec<Token>, ParseErr> {
    if s.trim().is_empty() {
        return Err(ParseErr::Empty);
    }
    let mut out = Vec::new();
    for part in s.split_whitespace() {
        if let Ok(n) = part.parse::<f64>() {
            out.push(Token::Num(n));
        } else if part.len() == 1 && "+-*/".contains(part) {
            out.push(Token::Op(part.chars().next().unwrap()));
        } else {
            return Err(ParseErr::BadChar(part.chars().next().unwrap()));
        }
    }
    Ok(out)
}
```

Проверено: `"1 + 2"` даёт три токена, пустая строка — «пустой ввод», `"1 ? 2"` — «недопустимый символ '?'».

**Типичные ошибки.**

- Тип ошибки `String` — вызывающий код не сможет её различить.
- Токены как кортежи `(String, String)` — теряется типобезопасность.
- `unwrap()` вместо возврата ошибки.
- Отсутствие `Display` — тогда ошибку нельзя показать пользователю.

**Развитие.** «Как избежать `to_string()` для каждого токена?» — хранить `&'a str` со временем жизни входа; обсудите компромисс. «Что даст `thiserror`?» — уберёт ручные `Display` и `From`, оставив атрибуты.

### Задача 2: LRU-кеш `[M]` · ~20 мин

**Условие.** Кеш фиксированного размера с вытеснением наименее недавно использованного.

**На что смотрит интервьюер.**

- Понимает ли, что нужны две структуры: карта для поиска и порядок использования.
- Обновляет ли позицию при `get`, а не только при `put`.
- Удаляет ли ключ из карты при вытеснении.
- Оговаривает ли сложность.

**Решение (упрощённое, O(n) на обновление порядка).**

```rust
struct Lru<K, V> {
    cap: usize,
    order: Vec<K>,
    map: HashMap<K, V>,
}

impl<K: Hash + Eq + Clone, V> Lru<K, V> {
    fn get(&mut self, k: &K) -> Option<&V> {
        if self.map.contains_key(k) {
            self.order.retain(|x| x != k);
            self.order.push(k.clone());
            self.map.get(k)
        } else {
            None
        }
    }

    fn put(&mut self, k: K, v: V) {
        if self.map.contains_key(&k) {
            self.order.retain(|x| x != &k);
        } else if self.map.len() == self.cap {
            let oldest = self.order.remove(0);
            self.map.remove(&oldest);
        }
        self.order.push(k.clone());
        self.map.insert(k, v);
    }
}
```

Проверено: при ёмкости 2 после `put(a)`, `put(b)`, `get(a)`, `put(c)` вытеснен `b`, а `a` остался.

**Важно проговорить вслух:** это решение за O(n) на обновление порядка. Классическое O(1) требует двусвязного списка, а он в безопасном Rust неудобен — нужен либо `Rc<RefCell<>>`, либо арена с индексами, либо готовый крейт `lru`. **Умение назвать это ограничение важнее, чем реализовать список.**

**Типичные ошибки.**

- `get` не обновляет порядок — тогда это не LRU.
- Вытеснение из порядка без удаления из карты — утечка.
- Попытка сразу писать двусвязный список и застревание на заимствованиях.
- Молчание про сложность.

**Развитие.** «Как сделать O(1)?» — арена: `Vec` узлов, ссылки индексами. «Как добавить время жизни записей?» — метка времени и ленивая проверка при обращении.

### Задача 3: свой итератор `[M]` · ~15 мин

**Условие.** Реализуйте тип, выдающий последовательность (например, числа Фибоначчи или счётчик), и покажите, что с ним работают адаптеры.

**На что смотрит интервьюер.**

- Знает ли, что нужен один метод `next` и ассоциированный тип `Item`.
- Понимает ли, что все адаптеры появляются бесплатно.
- Не пишет ли ручной цикл там, где работает цепочка.

**Решение.**

```rust
struct Counter { n: u32 }

impl Iterator for Counter {
    type Item = u32;

    fn next(&mut self) -> Option<u32> {
        if self.n < 5 {
            self.n += 1;
            Some(self.n)
        } else {
            None
        }
    }
}

let total: u32 = Counter { n: 0 }.filter(|n| n % 2 == 0).sum();
```

Проверено: сумма чётных из ряда 1..=5 равна 6.

Один реализованный метод — и тип встроился во всю экосистему: `map`, `filter`, `zip`, `take`, `collect`. Это лучшая иллюстрация того, зачем нужны трейты.

**Типичные ошибки.**

- Реализация лишних методов вручную.
- Обобщённый параметр вместо ассоциированного типа.
- Забытое условие остановки — бесконечный итератор без `take`.

**Развитие.** «Почему `Item` — ассоциированный тип, а не параметр?» — у итератора один тип элемента, иначе пришлось бы указывать его при каждом вызове. «Как сделать итератор по своей коллекции?» — реализовать `IntoIterator` для типа и для ссылки на него.

### Задача 4: группировка по ключу `[M]` · ~12 мин

**Условие.** Обобщённая функция, группирующая элементы по ключу, вычисляемому функцией.

**На что смотрит интервьюер.**

- Владеет ли обобщениями с ограничениями и параметром-замыканием.
- Знает ли `entry().or_default()`.
- Правильно ли расставляет владение: элементы перемещаются в группы.

**Решение.**

```rust
fn group_by<T, K: Hash + Eq, F: Fn(&T) -> K>(items: Vec<T>, key: F) -> HashMap<K, Vec<T>> {
    let mut out: HashMap<K, Vec<T>> = HashMap::new();
    for item in items {
        out.entry(key(&item)).or_default().push(item);
    }
    out
}
```

Проверено: три записи по двум городам дали группы размером 2 и 1.

Две детали: `items: Vec<T>` по значению, потому что элементы переезжают в группы; `key(&item)` по ссылке, потому что элемент нужен дальше. Именно на этой паре кандидаты чаще всего спотыкаются.

**Типичные ошибки.**

- Приём `&[T]` с последующим клонированием каждого элемента.
- `key(item)` по значению — элемент будет поглощён и `push` не скомпилируется.
- `or_insert(Vec::new())` вместо `or_default()` — создаёт вектор всегда.
- Забытое ограничение `Hash + Eq`.

**Развитие.** «Как сохранить порядок групп?» — `IndexMap` из одноимённого крейта либо дополнительный вектор ключей. «Как сделать по ссылкам без перемещения?» — вернуть `HashMap<K, Vec<&T>>` со временем жизни входа.

### Задача 5: конфигурация с валидацией `[M]` · ~18 мин

**Условие.** Разобрать конфигурацию, проверить обязательные поля, подставить умолчания и вернуть все нарушения сразу.

**На что смотрит интервьюер.**

- Различает ли «не задано» и «задано нулём» через `Option`.
- Собирает ли все ошибки, а не падает на первой.
- Использует ли типы для гарантий вместо проверок в рантайме.

**Ключевые решения.**

```rust
struct RawConfig {
    addr: Option<String>,
    workers: Option<usize>,
}

struct Config {
    addr: String,
    workers: usize,
}

fn validate(raw: RawConfig) -> Result<Config, Vec<String>> {
    let mut errs = Vec::new();

    let addr = raw.addr.unwrap_or_else(|| ":8080".to_string());
    if addr.is_empty() {
        errs.push("addr: пустое значение".to_string());
    }

    let workers = raw.workers.unwrap_or(4);
    if workers == 0 {
        errs.push("workers: должно быть больше нуля".to_string());
    }

    if errs.is_empty() {
        Ok(Config { addr, workers })
    } else {
        Err(errs)
    }
}
```

Главный приём — **два типа**: «сырой» с `Option` для разбора и «проверенный» без них. После валидации остальной код работает с типом, в котором все поля гарантированно корректны, — проверять их повторно не нужно.

**Типичные ошибки.**

- Один тип с `Option` во всех полях: каждая функция дальше вынуждена их разворачивать.
- Возврат первой ошибки — пользователь чинит конфиг по одной строке.
- Валидация при первом использовании вместо старта.
- `usize` без `Option` в сыром типе: ноль неотличим от отсутствия.

**Развитие.** «Как это связано с типизированным состоянием?» — тот же принцип: невозможные состояния непредставимы. «Что даст `serde`?» — разбор в сырой тип с `#[serde(default)]`, валидация остаётся вашей.
