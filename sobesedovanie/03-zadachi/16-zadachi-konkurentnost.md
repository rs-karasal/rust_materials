# 16. Задачи на конкурентность и async

> ⏱ **~90 минут** на проработку · 5 задач по 20–25 минут · грейды `[M]` `[S]`

Главная секция live-coding для позиций, где Rust выбран ради производительности. Здесь проверяют не знание синтаксиса `async`, а понимание: что живёт через `.await`, кто владеет данными и что произойдёт при отмене.

Все решения проверены запуском на `tokio`.

---

## Что проверяют в этой секции

1. **Владение между задачами.** `Arc` там, где нужно разделение, перемещение там, где достаточно.
2. **Ограничен ли параллелизм.** Запуск тысячи задач без предела — красный флаг.
3. **Понимает ли, что `async` не распараллеливает сам по себе.**
4. **Как обрабатываются ошибки и отмена.**

---

### Задача 1: параллельный запуск вместо последовательного `[M]` · ~15 мин

**Условие.** Дан список запросов. Выполните их конкурентно и соберите результаты.

**На что смотрит интервьюер.**

- Понимает ли, что `.await` в цикле даёт последовательность.
- Знает ли инструменты: `join!`, `join_all`, `JoinSet`.
- Различает ли конкурентность в одной задаче и распределение по потокам.

**Решение и замер.**

```rust
// последовательно — 103 мс
let _ = work(1, 50).await;
let _ = work(2, 50).await;

// конкурентно — 51 мс
let (a, b) = tokio::join!(work(1, 50), work(2, 50));
```

Проверено: две операции по 50 мс дали 103 мс последовательно и 51 мс через `join!`. Разница ровно та, что ожидается.

Для динамического числа задач берут `futures::future::join_all` или `tokio::spawn` с последующим ожиданием дескрипторов. Разница: `join!` выполняет будущие конкурентно **в одной задаче**, `spawn` отдаёт их рантайму, и они могут пойти на разные потоки.

**Типичные ошибки.**

- `.await` внутри цикла и уверенность, что это параллельно.
- `spawn` без сохранения дескрипторов — результаты и паники теряются.
- Запуск всех задач сразу без ограничения.

**Развитие.** «Как ограничить до N одновременных?» — семафор или `buffer_unordered(n)`. «Что если одна упала?» — `try_join!` прерывает остальные, `join_all` дожидается всех.

### Задача 2: ограничение параллелизма семафором `[M]` · ~20 мин

**Условие.** Обработать 10 задач, но не более 2 одновременно.

**На что смотрит интервьюер.**

- Знает ли `tokio::sync::Semaphore`.
- Захватывает ли разрешение **внутри** задачи, а не до `spawn`.
- Понимает ли, зачем `Arc` вокруг семафора.
- Освобождает ли разрешение автоматически (страж) или вручную.

**Решение.**

```rust
let sem = Arc::new(Semaphore::new(2));
let mut handles = Vec::new();

for i in 0..10u32 {
    let sem = Arc::clone(&sem);
    handles.push(tokio::spawn(async move {
        let _permit = sem.acquire().await.unwrap();
        // работа
        i
    }));
}

for h in handles {
    let _ = h.await.unwrap();
}
```

Проверено счётчиком: максимум одновременно активных задач равен 2, все 10 отработали.

Разрешение освобождается в `Drop` стража `_permit` — забыть невозможно. Обратите внимание на имя с подчёркиванием: без привязки к переменной страж уронился бы сразу и ограничение не работало бы.

**Типичные ошибки.**

- `let _ = sem.acquire().await` — страж уничтожается немедленно, ограничения нет.
- Захват разрешения до `spawn` — тогда 10 задач уже созданы и ждут.
- Забытый `Arc` — семафор не получится переместить в несколько задач.
- Использование обычного `std::sync::Mutex` как семафора.

**Развитие.** «Чем это отличается от пула воркеров?» — семафор ограничивает параллелизм, но задачи всё равно создаются все; пул создаёт фиксированное число исполнителей. «Как выбрать предел?» — по ограничениям зависимости: размер пула соединений, лимит внешнего API.

### Задача 3: разделяемое состояние между потоками `[M]` · ~15 мин

**Условие.** Сто потоков увеличивают общий счётчик. Обеспечьте корректность.

**На что смотрит интервьюер.**

- Знает ли связку `Arc<Mutex<T>>` и порядок вложенности.
- Понимает ли, почему `Rc` не подойдёт.
- Освобождает ли замок вовремя.
- Предложит ли `AtomicUsize` для счётчика — это правильнее.

**Решение.**

```rust
let counter = Arc::new(Mutex::new(0));
let mut handles = Vec::new();

for _ in 0..100 {
    let c = Arc::clone(&counter);
    handles.push(std::thread::spawn(move || {
        *c.lock().unwrap() += 1;
    }));
}

for h in handles {
    h.join().unwrap();
}
```

Проверено: результат ровно 100 при каждом запуске.

**Важно проговорить:** для одного числа мьютекс избыточен — `AtomicUsize` с `fetch_add` быстрее и не может привести к взаимоблокировке. Мьютекс нужен, когда согласованно меняются два и более поля.

**Типичные ошибки.**

- `Rc` вместо `Arc` — не скомпилируется, и это хорошо.
- `Mutex<Arc<T>>` вместо `Arc<Mutex<T>>` — каждый поток получит свой мьютекс.
- Удержание замка дольше необходимого.
- Игнорирование результата `join` — паника в потоке останется незамеченной.

**Развитие.** «Почему `lock()` возвращает `Result`?» — отравление после паники под замком. «Когда `RwLock`?» — при заметном перевесе чтений и длинных секциях, по замеру.

### Задача 4: операция с таймаутом и отменой `[M/S]` · ~20 мин

**Условие.** Выполнить операцию, но не дольше заданного времени. Объяснить, что произойдёт с незавершённой работой.

**На что смотрит интервьюер.**

- Знает ли `tokio::time::timeout`.
- **Понимает ли, что при таймауте задача отменяется мгновенно**, на последней точке `.await`.
- Может ли назвать, когда это опасно.

**Решение.**

```rust
match tokio::time::timeout(Duration::from_millis(20), work(3, 100)).await {
    Ok(v) => println!("успели {v}"),
    Err(_) => println!("таймаут сработал"),
}
```

Проверено: операция на 100 мс с таймаутом 20 мс дала ветку таймаута.

**Ключевой вопрос секции:** что стало с операцией? Она отменена — будущее уронено, и незавершённая работа исчезла без уведомления. Если внутри была запись в файл или транзакция, состояние может остаться частичным.

Это принципиально отличается от Go, где контекст — кооперативный сигнал, и функция сама решает, когда выйти.

**Типичные ошибки.**

- Уверенность, что задача «получит сигнал и завершится корректно».
- Оборачивание в таймаут операции, которую нельзя прерывать.
- Отсутствие таймаутов на внешних вызовах вовсе.

**Развитие.** «Как защитить неразрывную операцию?» — вынести в `tokio::spawn`: отдельная задача переживёт отмену, и её можно дождаться. «Что такое cancel safety?» — свойство операции корректно переживать прерывание на `.await`; в документации `tokio` указано для каждого метода.

### Задача 5: конвейер на каналах `[M/S]` · ~25 мин

**Условие.** Производитель отправляет данные, потребитель обрабатывает. Обеспечьте корректное завершение и обратное давление.

**На что смотрит интервьюер.**

- Использует ли ограниченный канал ради обратного давления.
- Понимает ли, что цикл получения завершается при освобождении всех отправителей.
- Обрабатывает ли ошибку `send` — она возникает, если получатель исчез.

**Решение.**

```rust
let (tx, mut rx) = tokio::sync::mpsc::channel(4);

tokio::spawn(async move {
    for i in 0..3 {
        if tx.send(i).await.is_err() {
            break;   // получатель исчез
        }
    }
    // tx уронится здесь — канал закроется
});

while let Some(v) = rx.recv().await {
    // обработка
}
```

Проверено: получены все три значения, цикл завершился сам.

Два момента, которые надо проговорить. **Ёмкость канала — это обратное давление**: когда буфер полон, `send` приостанавливается, и быстрый производитель притормаживает. Неограниченный канал такой защиты не даёт и позволяет памяти расти бесконечно.

**Завершение** происходит автоматически: когда последний отправитель уронен, `recv` возвращает `None`. Явно закрывать канал не нужно — за это отвечает владение.

**Типичные ошибки.**

- Неограниченный канал по умолчанию.
- Удержание клона `tx` в основной задаче — цикл `recv` не завершится никогда.
- Игнорирование ошибки `send` — задача продолжит работать впустую.
- Попытка «закрыть канал» вручную по аналогии с Go.

**Развитие.** «Как сделать несколько потребителей?» — `mpsc` не подходит, нужен `broadcast` или `async-channel`. «Как остановить конвейер снаружи?» — `CancellationToken` из `tokio-util` в `select!` вместе с `recv`.

---

## Чек-лист перед секцией

Соберите из головы, не подглядывая:

- конкурентный запуск через `join!` и через `spawn` с дескрипторами;
- ограничение параллелизма семафором с захватом внутри задачи;
- `Arc<Mutex<T>>` и понимание, когда достаточно атомарного счётчика;
- таймаут и ответ на вопрос «что стало с отменённой работой»;
- канал с ограниченной ёмкостью и автоматическое завершение по владению.

Главное отличие секции на Rust от аналогичной на Go: **здесь спрашивают про отмену**. Ответ «задача просто перестанет опрашиваться и исчезнет на последней точке `.await`» — то, что отделяет практика от читателя документации.
