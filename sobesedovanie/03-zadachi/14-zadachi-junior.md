# 14. Задачи уровня junior

> ⏱ **~60 минут** на проработку · 5 задач по 10–15 минут · грейд `[J]`

Задачи секции live-coding для junior. В Rust они проверяют не алгоритмы, а владение: справится ли человек, не расставляя `clone()` при каждой ошибке компилятора.

Все решения проверены запуском на актуальном компиляторе.

---

## Как оценивают live-coding на Rust

Порядок важности:

1. **Уточнил ли требования.** Юникод? Пустой вход? Регистр?
2. **Как борется с компилятором.** Читает сообщение и исправляет причину — или подбирает `clone()` и `&` наугад. Это главное отличие от секций на других языках.
3. **Идиоматичность.** Итераторы вместо ручных циклов, `&str` в параметрах, `Option`/`Result` вместо флагов.
4. **Граничные случаи.** Пусто, один элемент, юникод, `None`.
5. **Проговаривает ли решение.**

Компилятор здесь — третий участник разговора. Кандидат, который говорит «сейчас он скажет, что я переместил значение, поэтому возьму ссылку», сильнее того, кто молча правит код до зелёной сборки.

### Задача 1: развернуть строку `[J]` · ~8 мин

**Условие.** Напишите функцию, возвращающую строку задом наперёд.

**На что смотрит интервьюер.**

- Спросит ли про юникод.
- Знает ли, что `chars()` даёт кодовые точки, а не байты.
- Не станет ли работать с `as_bytes()` для кириллицы.
- Понимает ли, что задача решается одной строкой.

**Решение.**

```rust
fn reverse(s: &str) -> String {
    s.chars().rev().collect()
}
```

Проверено: `reverse("привет")` даёт `тевирп`, `reverse("rust")` — `tsur`.

Обратите внимание на сигнатуру: параметр `&str`, возврат `String`. Это каноническое распределение — заимствованный тип на входе, владеющий на выходе.

**Типичные ошибки.**

- Параметр `&String` вместо `&str`.
- Работа с байтами — кириллица рассыплется.
- Ручной цикл с индексами вместо итератора.
- Сборка через `push_str` в цикле, когда есть `collect`.

**Развитие.** «А если в строке эмодзи с модификатором кожи?» — `chars()` разделит его на составляющие; нужны графемные кластеры и внешний крейт `unicode-segmentation`. Ждут понимания проблемы, а не решения.

### Задача 2: проверить палиндром `[J]` · ~12 мин

**Условие.** Игнорируя регистр и знаки препинания. Пример: «А роза упала на лапу Азора».

**На что смотрит интервьюер.**

- Использует ли `is_alphanumeric` вместо перечисления символов.
- Понимает ли, что `to_lowercase` возвращает `String` (длина может измениться).
- Не разворачивает ли строку целиком ради сравнения.

**Решение.**

```rust
fn is_palindrome(s: &str) -> bool {
    let cleaned: Vec<char> = s
        .to_lowercase()
        .chars()
        .filter(|c| c.is_alphanumeric())
        .collect();
    cleaned.iter().eq(cleaned.iter().rev())
}
```

Проверено: фраза про розу даёт `true`, «привет» — `false`.

Метод `eq` у итераторов сравнивает две последовательности поэлементно — короче, чем цикл с двумя индексами, и без риска ошибиться в границах.

**Типичные ошибки.**

- Сборка развёрнутой строки и сравнение — лишняя аллокация.
- Фильтрация только пробелов.
- `to_lowercase()` внутри цикла на каждом символе.
- Работа с байтами.

**Развитие.** «Как обойтись без выделения вектора?» — два итератора с двух концов через `chars()` и `rev()`, пропуская неподходящие символы. Просят описать подход.

### Задача 3: топ-N частых слов `[J]` · ~15 мин

**Условие.** Вернуть N самых частых слов; при равной частоте — по алфавиту.

**На что смотрит интервьюер.**

- Знает ли идиому `*map.entry(k).or_insert(0) += 1`.
- Помнит ли, что `HashMap` не хранит порядок, и сортирует явно.
- Реализует ли вторичный критерий — без него результат нестабилен.
- Обработает ли `n` больше числа уникальных слов.

**Решение.**

```rust
fn top_words(text: &str, n: usize) -> Vec<(String, usize)> {
    let mut freq: HashMap<String, usize> = HashMap::new();
    for w in text.to_lowercase().split_whitespace() {
        let w = w.trim_matches(|c: char| !c.is_alphanumeric());
        if !w.is_empty() {
            *freq.entry(w.to_string()).or_insert(0) += 1;
        }
    }

    let mut pairs: Vec<(String, usize)> = freq.into_iter().collect();
    pairs.sort_by(|a, b| b.1.cmp(&a.1).then(a.0.cmp(&b.0)));
    pairs.truncate(n);
    pairs
}
```

Проверено на «мама мыла раму. Мама мыла окно!» с `n=2`: `[("мама", 2), ("мыла", 2)]` — порядок при равной частоте алфавитный и стабильный.

Метод `then` у `Ordering` — идиоматичный способ задать вторичный критерий; `truncate` безопасен при `n` больше длины, отдельная проверка не нужна.

**Типичные ошибки.**

- Возврат без сортировки — «работает» на одном запуске.
- Отсутствие вторичного критерия.
- `pairs[..n]` вместо `truncate` — паника при коротком векторе.
- Проверка `contains_key` перед вставкой вместо `entry`.

**Развитие.** «Как избежать `to_string()` на каждое слово?» — хранить `&str` с временем жизни исходного текста, но тогда результат нельзя пережить входную строку. Хороший повод обсудить компромисс.

### Задача 4: уникальные элементы с сохранением порядка `[J]` · ~10 мин

**Условие.** Из среза убрать повторы, сохранив порядок первого появления.

**На что смотрит интервьюер.**

- Использует ли `HashSet`, а не вложенный цикл.
- Знает ли, что `insert` возвращает `bool` — это позволяет фильтровать одним проходом.
- Правильно ли расставляет ограничения обобщения.

**Решение.**

```rust
fn unique<T: Eq + Hash + Clone>(items: &[T]) -> Vec<T> {
    let mut seen = HashSet::with_capacity(items.len());
    items
        .iter()
        .filter(|v| seen.insert((*v).clone()))
        .cloned()
        .collect()
}
```

Проверено: `[1, 2, 2, 3, 1]` даёт `[1, 2, 3]`, работает и для строк.

Приём с `insert` внутри `filter` — идиоматичный: метод возвращает `true`, если значение новое, поэтому фильтрация и запоминание происходят за один шаг.

**Типичные ошибки.**

- Вложенный цикл — квадратичная сложность.
- Ограничение конкретным типом вместо обобщения.
- Забытый `Hash` в ограничениях — компилятор напомнит.
- Два клона на элемент вместо одного.

**Развитие.** «Как обойтись без `Clone`?» — принимать `Vec<T>` по значению и возвращать его же, тогда клонировать не нужно. «А если тип не хешируем?» — `Vec` вместо `HashSet` и линейный поиск, то есть O(n²).

### Задача 5: слить два отсортированных среза `[J]` · ~12 мин

**Условие.** Вернуть один отсортированный вектор со всеми элементами.

**На что смотрит интервьюер.**

- Реализует ли слияние двумя индексами за один проход.
- Резервирует ли ёмкость.
- Не забудет ли остатки.
- Обработает ли пустые срезы.

**Решение.**

```rust
fn merge_sorted(a: &[i32], b: &[i32]) -> Vec<i32> {
    let mut out = Vec::with_capacity(a.len() + b.len());
    let (mut i, mut j) = (0, 0);
    while i < a.len() && j < b.len() {
        if a[i] <= b[j] {
            out.push(a[i]);
            i += 1;
        } else {
            out.push(b[j]);
            j += 1;
        }
    }
    out.extend_from_slice(&a[i..]);
    out.extend_from_slice(&b[j..]);
    out
}
```

Проверено: `[1, 3, 5]` и `[2, 4]` дают `[1, 2, 3, 4, 5]`; пустой срез с `[1]` в любом порядке даёт `[1]`.

Остатки дописываются без условий: если элементы кончились, срез пустой и `extend_from_slice` ничего не делает. Это убирает две ветки и типичную ошибку «забыл хвост».

**Типичные ошибки.**

- Конкатенация с последующей сортировкой — O(n log n) вместо O(n).
- Забытый остаток.
- Отдельные ветки для пустых срезов — не нужны.
- `<` вместо `<=`: нарушится устойчивость при равных элементах.

**Развитие.** «А если срезов K?» — попарное слияние даёт O(nK), куча (`BinaryHeap`) — O(n log K). «Как обобщить по типу?» — `T: Ord + Copy`, и обсудить, почему `Copy`, а не `Clone`.

## Чек-лист перед секцией

- Разворот и обход строки через `chars()`, а не байты.
- Частотный словарь через `entry().or_insert()`.
- Сортировка с вторичным критерием через `then`.
- Уникальные элементы через `HashSet::insert` в `filter`.
- Слияние двумя индексами с дописыванием остатков срезами.

И главное правило секции на Rust: **читайте сообщение компилятора вслух**. Оно почти всегда содержит и причину, и решение, а привычка проговаривать его показывает интервьюеру, что вы работаете с языком, а не воюете.
