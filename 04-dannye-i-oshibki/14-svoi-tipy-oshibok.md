# 14. Свои типы ошибок: `From`, `thiserror`, `anyhow`

> ⏱ **~55 минут** · теория 20 мин · практика 35 мин

В прошлой статье ошибки были чужие — из стандартной библиотеки. Как только программа делает что-то своё, ей нужен собственный тип ошибки: «не найден ключ конфигурации», «пользователь заблокирован». Разберём, как такой тип устроен вручную, а потом — два крейта, которыми это делают в реальных проектах.

## Свой тип ошибки вручную

Ошибка — обычно перечисление всех способов, которыми операция может не удаться:

```rust
#[derive(Debug)]
enum ConfigError {
    Missing(String),
    BadNumber(ParseIntError),
}
```

Чтобы тип считался полноценной ошибкой, от него ждут трёх вещей.

**`Debug`** — для отладочного вывода, обычно через `derive`.

**`Display`** — сообщение для человека. Реализуется вручную:

```rust
impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ConfigError::Missing(key) => write!(f, "не найден ключ «{key}»"),
            ConfigError::BadNumber(e) => write!(f, "не удалось разобрать число: {e}"),
        }
    }
}
```

**Трейт `Error`** — маркер «это ошибка». Если `Debug` и `Display` уже есть, реализация пустая:

```rust
impl std::error::Error for ConfigError {}
```

## `From` и магия `?`

Теперь ключевой момент. Помните обещание из прошлой статьи, что `?` умеет преобразовывать типы ошибок? Механизм — трейт `From`:

```rust
impl From<ParseIntError> for ConfigError {
    fn from(e: ParseIntError) -> Self {
        ConfigError::BadNumber(e)
    }
}
```

После этого `?` сам превращает чужую ошибку в вашу:

```rust
fn read_port(raw: Option<&str>) -> Result<u16, ConfigError> {
    let raw = raw.ok_or_else(|| ConfigError::Missing(String::from("port")))?;
    let port: u16 = raw.trim().parse()?;      // ParseIntError → ConfigError
    Ok(port)
}
```

```
Ok(8080)
не найден ключ «port»
не удалось разобрать число: invalid digit found in string
```

Во второй строке — новый метод: `ok_or_else` превращает `Option` в `Result`, подставляя ошибку вместо `None`. Пара `ok_or` / `ok_or_else` — мост между двумя типами, и встречается она постоянно.

Итог: тело функции читается как последовательность шагов, а весь перевод ошибок происходит в объявлениях `From`.

## `thiserror`: то же самое без рутины

Писать `Display` и `From` руками для каждого варианта — скучно. Крейт `thiserror` генерирует их из атрибутов:

```rust
use thiserror::Error;

#[derive(Debug, Error)]
enum ConfigError {
    #[error("не найден ключ «{0}»")]
    Missing(String),

    #[error("не удалось разобрать число")]
    BadNumber(#[from] ParseIntError),
}
```

Двенадцать строк превратились в шесть, а поведение то же:

```
не найден ключ «port»
не удалось разобрать число
```

Что делают атрибуты:

- `#[error("...")]` — задаёт текст `Display`. В фигурных скобках доступны поля варианта: `{0}` для кортежных, `{имя}` для именованных.
- `#[from]` — генерирует реализацию `From`, чтобы `?` работал автоматически.
- `#[source]` — помечает вложенную ошибку-причину, если её не покрывает `#[from]`.

`thiserror` работает только на этапе компиляции: в готовой программе от него не остаётся ничего, кроме кода, который вы написали бы руками.

## `anyhow`: когда тип ошибки не важен

Есть вторая ситуация. В приложении — в отличие от библиотеки — вызывающему коду обычно не нужно разбирать ошибку по вариантам: её надо показать пользователю и завершиться. Заводить перечисление ради этого излишне.

Для таких случаев есть `anyhow::Result<T>` — сокращение для «результат с какой угодно ошибкой»:

```rust
use anyhow::{Context, Result};

fn load() -> Result<String> {
    let text = std::fs::read_to_string("нет-файла.toml")
        .context("не удалось прочитать конфигурацию приложения")?;
    Ok(text)
}
```

Главная ценность — метод `context`: он добавляет к ошибке слой объяснения, не теряя исходную причину:

```
не удалось прочитать конфигурацию приложения

Caused by:
    No such file or directory (os error 2)
```

Сравните с голым «No such file or directory» — из него непонятно, какой файл и зачем читали. Привычка навешивать `context` на каждый `?` превращает логи в связный рассказ.

## Что выбрать

| Ситуация | Инструмент |
|---|---|
| **Библиотека**: вызывающий код должен различать причины сбоя | `thiserror` — конкретное перечисление |
| **Приложение**: ошибку показывают и выходят | `anyhow` — `Result<T>` плюс `context` |
| Учебный код и прототипы | `Box<dyn Error>` из стандартной библиотеки |

Правило, принятое в сообществе: **`thiserror` для библиотек, `anyhow` для приложений**. Оно объясняется просто. Библиотека не знает, как её ошибку будут обрабатывать, поэтому обязана дать точный тип. Приложение — конечная точка, и ему важнее удобство.

Крейты не конфликтуют: типичный проект использует `thiserror` во внутренних модулях и `anyhow` в `main`.

Отдельно про `Box<dyn Error>` — «любая ошибка» средствами стандартной библиотеки, без зависимостей. Именно его предлагал компилятор в прошлой статье. Работает, но не умеет добавлять контекст, поэтому в приложениях его вытеснил `anyhow`.

## Что запомнить

- Свой тип ошибки — обычно перечисление; от него ждут `Debug`, `Display` и трейт `Error`.
- `?` преобразует чужую ошибку в вашу через трейт `From` — именно поэтому тело функции остаётся чистым.
- `ok_or` / `ok_or_else` превращают `Option` в `Result`.
- `thiserror` генерирует `Display` и `From` из атрибутов `#[error("...")]` и `#[from]`; в рантайме не стоит ничего.
- `anyhow::Result<T>` подходит, когда тип ошибки не важен, а метод `context` добавляет объяснение, сохраняя причину.
- Соглашение: `thiserror` в библиотеках, `anyhow` в приложениях; вместе они не конфликтуют.
- `Box<dyn Error>` — вариант без зависимостей, но без контекста.

## Практика

**1. Ошибка вручную.** Опишите перечисление `ValidationError` с вариантами «слишком короткое имя» и «недопустимый возраст». Реализуйте `Debug`, `Display` и `Error` без крейтов. Готово, когда ошибка печатается человекочитаемо через `{}`.

**2. Мост через `From`.** Добавьте вариант, оборачивающий `ParseIntError`, и реализацию `From`. Напишите функцию, где `?` преобразует ошибку разбора в вашу. Готово, когда в теле функции нет ни одного явного преобразования.

**3. Переезд на `thiserror`.** Перепишите тот же тип через `thiserror`, сохранив тексты сообщений. Сравните количество строк. Готово, когда поведение не изменилось, а ручных `impl` не осталось.

**4. Контекст в `anyhow`.** Напишите функцию, читающую два файла подряд, каждый вызов снабдите своим `context`. Запустите на отсутствующем файле и посмотрите на цепочку `Caused by`. Готово, когда из вывода понятно, какой именно файл не открылся.

**5. Выбор инструмента.** Для трёх случаев решите, что использовать, и обоснуйте: библиотека разбора CSV; утилита командной строки, конвертирующая файлы; внутренний модуль большого приложения, чьи ошибки обрабатывает соседний модуль. Готово, когда для каждого есть ответ с аргументом.
