# 13. `Result<T, E>`, оператор `?` и паника

> ⏱ **~55 минут** · теория 20 мин · практика 35 мин

В Rust нет исключений. Ошибка здесь — не особый механизм, который «выпрыгивает» из функции, а обычное значение, которое возвращают и обрабатывают. Такой подход делает видимым в сигнатуре то, что в других языках приходится узнавать из документации: может эта функция сломаться или нет.

## Две категории проблем

Rust различает их принципиально.

**Невосстановимые** — программа находится в состоянии, в котором продолжать бессмысленно: нарушен инвариант, обращение за границу массива, деление на ноль. Реакция — **паника**: выполнение прекращается.

**Восстановимые** — ожидаемая часть работы: файла нет, пользователь ввёл не число, сеть недоступна. Реакция — вернуть `Result` и дать вызывающему коду решить, что делать.

Ключевой вопрос при выборе: **может ли вызывающий код осмысленно отреагировать?** Если да — `Result`. Если нет и ситуация означает баг — паника.

## Паника

Вызывается макросом `panic!("сообщение")` или возникает сама при нарушении инвариантов языка:

```
thread 'main' panicked at u.rs:2:32:
ожидалось число: ParseIntError { kind: InvalidDigit }
```

Программа печатает сообщение, разматывает стек, освобождая данные, и завершается. Переменная окружения `RUST_BACKTRACE=1` покажет полную цепочку вызовов — первое, что стоит сделать при непонятной панике.

## `Result<T, E>`

Это перечисление, устроенное как `Option`, но с данными в обеих ветвях:

```rust
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

`T` — тип результата, `E` — тип ошибки. Разбирается тем же `match`:

```rust
match read_file("нет-такого.txt") {
    Ok(text) => println!("прочитано {} байт", text.len()),
    Err(e) => println!("ошибка: {e}"),
}
```

```
ошибка: No such file or directory (os error 2)
```

Обратите внимание на сигнатуру такой функции:

```rust
fn read_file(path: &str) -> Result<String, std::io::Error>
```

Здесь всё сказано: вернёт строку либо ошибку ввода-вывода. Ни документации, ни угадывания.

## `unwrap` и `expect`

Два метода достают значение из `Ok`, паникуя на `Err`:

```rust
let n: i32 = "abc".parse().unwrap();                        // паника без пояснений
let n: i32 = "abc".parse().expect("ожидалось число");       // паника с вашим текстом
```

Всегда предпочитайте `expect` с осмысленным текстом: сообщение попадёт в лог и объяснит, какое именно предположение нарушилось.

Когда это законно:

- в прототипах и учебном коде, где обработка отвлекает от сути;
- в тестах — там паника и есть способ провалить тест;
- когда вы **можете доказать**, что ошибка невозможна: например, разбираете строковую константу, написанную рядом в коде.

Мягкие альтернативы без паники — `unwrap_or(значение)`, `unwrap_or_default()`, `unwrap_or_else(|e| ...)`:

```rust
let n: Result<i32, _> = "5x".parse::<i32>();
println!("{}", n.unwrap_or(0));       // 0
```

## Оператор `?`

Писать `match` на каждый вызов — многословно. Оператор `?` делает то же самое одним символом:

```rust
fn read_file(path: &str) -> Result<String, std::io::Error> {
    let mut f = File::open(path)?;
    let mut s = String::new();
    f.read_to_string(&mut s)?;
    Ok(s)
}
```

`?` после выражения типа `Result` означает: **если `Ok` — достать значение и продолжить; если `Err` — немедленно вернуть эту ошибку из функции**.

Три строки вместо пятнадцати, и «счастливый путь» читается сверху вниз без вложенности. Именно так в Rust выглядит нормальная обработка ошибок.

Ограничение очевидно: раз `?` возвращает ошибку из функции, функция должна возвращать `Result`. Иначе:

```
error[E0277]: the `?` operator can only be used in a function that returns `Result`
 --> q.rs:2:31
  |
1 | fn main() {
  | --------- this function should return `Result` or `Option` to accept `?`
help: consider adding return type
  |
1 ~ fn main() -> Result<(), Box<dyn std::error::Error>> {
```

Компилятор сразу показывает решение: `main` тоже может возвращать `Result`. Такая программа завершится с ненулевым кодом и напечатает ошибку, если получит `Err`, — это стандартный приём для небольших утилит:

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let text = read_file("data.txt")?;
    println!("{text}");
    Ok(())
}
```

Строку `Ok(())` в конце легко забыть: `main` обязана вернуть значение, а «успех без данных» — это `Ok` от unit-типа.

С `Option` оператор `?` тоже работает: возвращает `None` из функции, если значение отсутствует.

## Ещё одно преимущество `?`

Есть тонкость, ради которой `?` любят особенно: он **автоматически преобразует тип ошибки**, если для него определено превращение в тип, объявленный в сигнатуре. Благодаря этому в одной функции можно вызывать код, возвращающий разные ошибки, и не писать преобразования руками.

Как этим управлять и как объявлять собственные типы ошибок — тема следующей статьи.

## Что запомнить

- Исключений нет: ошибка — это возвращаемое значение.
- Паника для невосстановимых ситуаций (баг в программе), `Result` — для ожидаемых (файла нет, ввод неверен).
- Критерий выбора: может ли вызывающий код осмысленно отреагировать.
- `Result<T, E>` — перечисление `Ok(T)` / `Err(E)`; тип ошибки виден прямо в сигнатуре функции.
- `unwrap` паникует молча, `expect` — с вашим сообщением; в рабочем коде оба допустимы только при доказуемой невозможности ошибки.
- `unwrap_or`, `unwrap_or_default`, `unwrap_or_else` дают значение по умолчанию без паники.
- `?` достаёт значение из `Ok` или досрочно возвращает `Err` из функции; требует, чтобы функция возвращала `Result` или `Option`.
- `main` может возвращать `Result` — тогда в конце пишут `Ok(())`.

## Практика

**1. Разбор строки.** Напишите функцию `parse_age(s: &str) -> Result<u8, std::num::ParseIntError>`. Вызовите её с корректным и некорректным вводом, обработайте оба случая через `match`. Готово, когда программа не паникует ни в одном случае.

**2. Три способа не упасть.** Один и тот же неудачный разбор обработайте через `unwrap_or`, `unwrap_or_default` и `match`. Сравните код. Готово, когда можете сказать, когда какой уместен.

**3. Цепочка с `?`.** Напишите функцию, которая читает файл и возвращает количество строк в нём, используя `?` минимум дважды. Вызовите её для существующего и несуществующего файла. Готово, когда в теле функции нет ни одного `match`.

**4. `main`, возвращающая `Result`.** Перепишите программу из задачи 3 так, чтобы `?` использовался прямо в `main`. Проверьте код возврата процесса командой `echo $?` после запуска. Готово, когда при ошибке код возврата не равен нулю.

**5. Паника или `Result`.** Для пяти ситуаций решите, что уместнее, и обоснуйте: деление на ноль по вводу пользователя; обращение к 10-му элементу вектора из 3; отсутствие конфигурационного файла; отрицательный возраст в структуре, который вы сами только что проверили; недоступность сети. Готово, когда для каждой есть ответ и аргумент.
